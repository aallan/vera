- **An `if` or a `match` that joins an `@Int` branch with a `@Nat` one, or with a refinement of `@Nat`, is an `@Int`, so binding it into a `@Nat` position is obligated** ([#1756](https://github.com/aallan/vera/issues/1756)).  The checker joined the two through the relaxed `Int <: Nat` rule, which gave an `if` whose then-branch is an `@Int` (a negated literal, literal arithmetic, an `@Int` slot or a sum over one) and whose else-branch is a `@Nat` the type `@Nat`, as it gave a `match` whose later arm is the `@Int`, and a join with a refinement of `@Nat` the refined type.  The verifier, reading that type, recorded no narrowing where the join was bound into a `@Nat` `let`, call argument or constructor field, while the compiled module guarded the binding: `let @Nat = if @Bool.0 then { -1 } else { @Nat.0 };` passed `vera verify`, and its run trapped.  The join is now an `@Int` unless every `@Int` branch is made only of non-negative literals and `@Nat` values, so the narrowing is obligated where the join is bound: refused (E503) where a branch can be negative, and recorded beside the module's guard where it cannot.  No program of the corpus, the examples or the docs' Vera blocks changes its verdict, its obligations or its compiled WAT.
  - Upgrade note: a program that verified with such a join and a branch that can be negative now fails with E503 at the binding; its run trapped there before.  E503's fix applies: a precondition ruling out the input its counterexample names, or a guard on the binding.
