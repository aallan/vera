- The nightly mutation sweep measures a random sample of the mutants mutmut makes in `vera/` instead of every one ([#1827](https://github.com/aallan/vera/issues/1827)): each mutant is in a cycle's sample, 2% of them (`SAMPLE_FRACTION`), by a hash of the cycle, the function and its number, so every job of a night and every night of the cycle draw the same sample and the next cycle draws another; every function is counted by mutmut's own visitor through the engine's new `count` command before the plan, and each slice's record carries the counts for the stitch. A cycle closes in a night or two, and `mutation-summary.csv` and the badge's `mutation.json` carry the score's 95% Wilson interval beside each module's population. The sweep that measured every mutant decided 300 to 1,300 of about 113,000 a night, so a cycle would have taken months of green nights against a tree that changes daily.
- Both mutation lanes run every pytest session in a process of its own, `process_isolation = "forkserver"` in `[tool.mutmut]` ([#1827](https://github.com/aallan/vera/issues/1827)): mutmut's default fork runner ran its stats pass, its test listing and its clean run as sessions of one process and forked the mutant workers from it, and state one session left behind broke the next on five nights (wasmtime's trap handlers put back by the faulthandler plugin, #1745 and #1747; a generator parametrisation consumed by the first collection, #1822). The fork server runs each session in a fresh child of a parent that never imports pytest.
