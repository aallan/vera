- A slice of the nightly mutation sweep survives the loss of its runner ([#1838](https://github.com/aallan/vera/issues/1838)). A lost runner takes its job's log with it and uploads nothing after the loss: on 11 November 2026 slice 0 lost its runner at +161 minutes and left neither a record nor a log, its one function the same that lost a runner on 7 and 10 November. The slice now runs in the background across the job's steps and rewrites its partial record at every heartbeat, and ten leg steps upload it as `mutation-sweep-slice-<n>-leg-<k>` (the plan, then every 30 minutes, kept three days). Every leg step and leg upload continues on error, so a leg that fails never ends the slice. A partial record never holds less than an earlier one: a `mutmut results` listing that fails keeps the results last read whole, and the record says when it failed. The stitch takes a slice's final record, whose name and shape are unchanged, and otherwise its legs together (a mutant any valid leg decided is decided; two legs that disagree leave it undecided and are a problem), and the slice counts as lost. A cancelled run charges no loss. The record's heartbeat series holds the runner's memory, swap, load and free disk and the bound's processes, memory and kill count.
- The nightly mutation sweep's engine runs under a memory bound: a transient systemd scope, set up with the hosted runner's own `sudo`, with `MemoryMax` at the runner's memory less 2.5 GiB, no swap, and `OOMPolicy=continue`, as the runner's user with its environment. The oracle plugin makes each mutant's run the kernel's first choice (`oom_score_adj` 1000, the engine 500), so a run that outgrows the bound ends and the runner lives. A bound that cannot be set stops the slice as a lane failure; it never runs unbounded. A mutant whose run the kernel ended there (the bound's `oom_kill` count rose while its process disappeared, and mutmut recorded the `-9` it reports as `segfault`) is `memory`; one in flight, having run at least five minutes, at the last record of two slices that ended with neither the engine finishing nor the budget stopping it is `lost`. Both are decided, counted apart and listed, never caught and never survived, and a slice lost two nights running on the same plan with nothing decided is red. The state stays schema 3: a unit's losses, the `memory` and `lost` columns and a night's lost plans are written only when they hold a fact.
- A `segfault` or `suspicious` mutant the engine recorded before a budget stop was sent is kept; only a status that appears after the stop is left undecided, in every record the slice writes. A budget stop whose final listing fails charges no loss. Each mutant's duration is its own run's, from the start to the end the oracle plugin records in the run; a run with no end (the cap's exit, a kill) has no measured duration: mutmut's fork server reports every duration as zero, and the calibration of the sweep's plan, which moved halfway to zero on each such night, now leaves a zero duration out.
- `scripts/mutate_diff.py`'s engine runner ends the engine's whole process group on any exception that ends its wait (a keyboard interrupt, a signal the caller turned into one, a test's timeout), where only its own budget did before. The diff lane runs without the memory bound: a worker the kernel ended there would read as a `segfault`, and what its result means stays as it is.
