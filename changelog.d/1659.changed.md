- **`matrix-gate` reads every cell's conclusion from the run's job listing** ([#1659](https://github.com/aallan/vera/issues/1659)).  The gate passed on the matrix job's result, the aggregate GitHub computes over the cells that ran in the current attempt, which reads `success` once one of two failed cells is re-run on its own and passes.  Wherever the matrix ran, `scripts/matrix_gate.py` now lists the run's jobs, `gh run view $GITHUB_RUN_ID --attempt $GITHUB_RUN_ATTEMPT --json jobs` with `actions: read`, and passes only when the listing holds as many cells as the matrix runs (the `test` job's new `cells` output, `strategy.job-total`) and every one of them, the advisory aarch64 cell apart, concluded `success`; a listing, run id, attempt or size it cannot read fails it, and a matrix skipped on a change that keeps the version passes as before.  A re-run attempt lists every job of the run, the ones it ran again and a copy of each other one with the conclusion it had, so re-running the failed jobs as a set passes the gate and re-running one of two failed cells does not.  `matrix-issue` names the cells the gate read as failed, where it used to list the run's jobs itself, and files where the gate found a failed cell beside a matrix result of `success`.
- **A release run that waits behind another runs in its turn.**  `release.yml`'s concurrency group gains `queue: max`: a group without a queue holds one pending run, which a newer arrival replaces, so a third push to `main` could drop a version-raising merge's release run while it waited behind another.
- **The full matrix's Linux x86_64 cells run on `ubuntu-24.04`, not `ubuntu-latest`**, the release README § Supported platforms names; GitHub moves `ubuntu-latest` to Ubuntu 26.04 over several weeks from 2026-10-19, and plans to finish by 2026-11-19.  The cells are named `test (ubuntu-24.04, 3.x)`.  The shards, whose names carry the runner and are required checks, and the other jobs stay on `ubuntu-latest`.
