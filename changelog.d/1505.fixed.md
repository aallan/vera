- **A message spells a type as the source writes it: a type argument has no `@`, a refinement keeps its predicate, and a function type is written out** ([#1505](https://github.com/aallan/vera/issues/1505)).  `ast.format_type_expr` rendered each type argument as a type in a slot's position, a refinement as its base and a function type as `@?`, so `vera verify --json`'s obligation descriptions, runtime contract and trap messages, diagnostics and the `vera check --explain-slots` header showed `@Array<@Int>.0`, which fails `vera check` with `E005` when pasted back, and read two parameters that differ only in a refinement's predicate as one type.  A type is now rendered by the canonical formatter, as `vera fmt` writes it: `requires(array_length(@Array<@Int>.0) > 0) failed` reads `requires(array_length(@Array<Int>.0) > 0) failed`, and `fn f(@Array<@Int>, @Array<@Int> -> @Int)` reads `fn f(@Array<{ @Int | @Int.0 > 0 }>, @Array<{ @Int | @Int.0 < 0 }> -> @Int)`.  The places that rebuilt the rendering themselves read it as it is:
  - `vera/addEffect` keys a handler by the bare rendering, so a handler whose argument holds a function type (`handle[Exn<Option<fn(Int -> Int) effects(pure)>>]`) bounds a request spelled the same; the key spelled the function type `?`, and the caller was given a row it did not need.
  - `E340`'s fix for a user-declared effect writes an operation declared further down the file with its refined parameters whole, where it wrote each one's base.
  - The message for an exception escaping an entry point names the row's type: `Exn<Array<{ @Int | @Int.0 >= 0 }>>` read `Exn<Array<Int>>`, and the `handle[Exn<Array<Int>>]` it asked for does not catch it.
  - The verifier's sentence for an operation in a refinement's predicate (`E526`, `E502` and the other operation diagnostics) names the refinement with its base's arguments bare and its predicate as `vera fmt` writes it.
