- **A refinement unifies by its base, on either side of a call's argument judgement and at every level of the type** (two lines of [#1684](https://github.com/aallan/vera/issues/1684)).  Type-argument inference unwrapped a refinement only on the argument's side against a data-type parameter, so a refined function type at a function-typed parameter left the callee's variable unbound, and a parameterised refinement alias at a parameter bound nothing: with `type Foo = { @fn(Int -> Int) effects(pure) | true }`, `array_map([1], @Foo.0)` was refused with `E202` (`expected fn(Int -> B)`), and with `type NE<T> = { @Array<T> | array_length(@Array<T>.0) > 0 }` and `forall<T> fn head_of(@NE<T> -> @T)`, `head_of(@NE<Int>.0) + 1` was `E140` (`found ? and Int`) while `nat_to_int(string_length(head_of(["abc", "d"])))` passed `vera check` and `vera verify` and built a module that did not load.  A refinement on either side now unifies by its base at every level, in every branch of the type (a data type, a function type, a tuple, an `Array`, a `Map`), so `B` is bound to `Int`, `head_of` is recorded at `Int` and at `String`, and the three programs run; the refinement's predicate stays the obligation the binding site records (`refine_bind`).  A constructor's field unifies by the same rule: with `data Holder<T> { Holder(NE<T>) }`, `Holder(["hello"])` binds `T` to `String` and runs, where it was refused with `E213` (`field 0 has type Array<String>, expected {@Array<T> | ...}`).  A result such a call typed as a wildcard is held to its type: `let @String = array_map([1], @Foo.0)[0]` is `E170`.  No example, conformance program or documentation example changes verdict.
