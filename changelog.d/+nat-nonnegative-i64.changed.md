- **`Nat` is the non-negative `Int` its definition says it is, `0 .. 2^63 - 1`, and every integer literal is an `Int`.  This change is breaking** ([#1504](https://github.com/aallan/vera/issues/1504)).  Spec §2.2 defines `Nat` as `{ @Int | @Int.0 >= 0 }`, and the compiler held it as an unsigned 64-bit integer in a signed slot, with a range no `Int` can hold: a literal could reach `2^64 - 1`, `@Nat` arithmetic was checked against the unsigned range, every place a `@Nat` met an `@Int` carried its own obligation and guard, and the operations that read a value's sign read a `@Nat` above `2^63 - 1` as the negative number its bits spell.  A `@Nat` is now an i64 whose value is non-negative.  Reading one as an `@Int` is a no-op; its arithmetic, comparisons, division and rendering are the `@Int` instructions; its `+` and `*` are checked against the i64 range, and its `-` against zero (`nat_sub`, as before).
  - A literal is an `Int` wherever it is written.  In a `@Nat` or refined context it is a narrowing, obligated as any `@Int` narrowing is: `let @Nat = 5` verifies and `let @Nat = 0 - 3` is refused (E503).  The sign of a literal no longer decides a type: `5 - 2` is an `Int`, `id(5)` with nothing expected is `id` at `Int`, and an expected `Nat` fixes a type argument whatever the literals' signs, so `let @Nat = second(-3, 5)` and `let @Nat = array_reverse([0 - 3, 5])[0]`, each of which verified and returned 5, are refused (E503) and trap at the negative literal (spec §4.2).
  - **Upgrade note.**  A program that held a `@Nat` above `9223372036854775807` cannot now.  A literal above that bound is E149 wherever it is written, a `@Nat` context and a literal pattern included, and a pattern over a `@Byte` is held to `0..255`.  An operation whose `@Nat` result would pass the bound carries the i64 overflow obligation, and traps (`overflow`) where the obligation is not proved; `abs(-9223372036854775808)` is one, since its result `2^63` is no `Nat`.  `parse_nat` returns `Err("out of range")` for a numeral above the bound, and `vera run` refuses a `@Nat` argument outside `0 .. 9223372036854775807`, and an `@Int` one outside the i64 range, instead of wrapping it.  `nat_to_int` stays, the identity, and is never needed to widen: a `@Nat` is an `@Int` as it stands.  A subtraction with a literal operand, `@Nat.0 - 1`, is an `@Int` subtraction: bound into a `@Nat` it is obligated there (`nat_bind`, E503) rather than as a `@Nat` subtraction (`nat_sub`, E502), and read as an `@Int` its value at 0 is -1 rather than an underflow trap.
