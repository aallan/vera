- **The type a value is expected at fixes what its arguments or elements leave open, and argument order never decides a type variable** ([#1684](https://github.com/aallan/vera/issues/1684)).  `let @Array<Option<Nat>> = [None, None]` was refused (`E170`, and `E121` as a return, `E171` as a closure's body); it now checks and runs.  `nat_to_int(string_length(head_plain([])))`, with `forall<T> fn head_plain(@Array<T> -> @T)`, compiled `head_plain` at a default type and its module did not load; the `String` parameter now fixes `T`.  A type variable two arguments give different types took the first argument's, so `second(fn(@Int -> @Int) ..., fn(@Nat -> @Int) ...)` applied to -5 ran the `Nat` closure on -5 with every gate green, and the other order was refused; it now takes the type the result is expected at where both fit it, otherwise the type they share (at a function's parameter, what both accept), in either order, and the -5 is refused (`E503`).  An array literal's element type follows the same rule, so `idg([@PosInt.0, @Int.0])` is no longer refused where `idg([@Int.0, @PosInt.0])` is accepted, and `[pure_fn, io_fn]` is accepted as `[io_fn, pure_fn]` was.  An empty literal takes its type from its context, and an index expected at a type reads an array of that type, so `let @Int = [][0];` compiles where code generation skipped the function.  A type the arguments' join gave stays provisional: a call nested as another generic call's argument takes the type the outer call is expected at, so a narrowing stays at the argument where the caller's facts prove it.  Spec §4.2, §4.8, §4.12.1, §5.9 and §11 state the rules.  An index no context types (`match [][0] { ... }`) is [#1862](https://github.com/aallan/vera/issues/1862)'s.
