- **The type a value is expected at fixes what its arguments or elements leave open, and argument order never decides a type variable** ([#1684](https://github.com/aallan/vera/issues/1684)).  `let @Array<Option<Nat>> = [None, None]` was refused (`E170`, and `E121` as a return, `E171` as a closure's body); it now checks and runs.  `nat_to_int(string_length(head_plain([])))`, with `forall<T> fn head_plain(@Array<T> -> @T)`, compiled `head_plain` at a default type and its module did not load; the `String` parameter now fixes `T`.  A type variable two arguments give different types took the first argument's, so `second(fn(@Int -> @Int) ..., fn(@Nat -> @Int) ...)` applied to -5 ran the `Nat` closure on -5 with every gate green, and the other order was refused; it now takes the type they share (at a function's parameter, what both accept), in either order and whatever the result is expected at, and the -5 is refused (`E503`).  Where the result is bound at the stronger type, `let @Nat = second(@Nat.0, @Int.0)` is `second` at `Int` in both orders, and the narrowing into `Nat` is the binding's, of the call's result, guarded at run time where the solver does not prove it; bind the `Int` argument at `Nat` first for a proof where it is passed.  So a narrowing of the argument that came second moves to where the result is bound: `pick(@Nat.0, @Int.0)` returned at `@Nat`, refused before (`E503`), now compiles with a run-time check at the return, and one the caller's facts proved at the argument is now that run-time check.  An indexed literal goes the other way: `[@Nat.0, @Int.0][1]` returned at `@Nat` was a run-time check at the `@Int` element and is now refused at the return (`E503`), as `[@Int.0, @Nat.0][0]` already was, and verifies with a precondition such as `requires(@Int.0 >= 0)`.  Binding the argument or element at the stronger type first keeps the narrowing where it was.  `second(@PosInt.0, @Small.0)`, two refinements of one base with different predicates, was refused (`E505` at whichever came second, an indexed literal of the two trapping on a valid value) and now joins at `Int` and verifies, in either order.  An array literal's element type is its elements' shared type where nothing is expected of it, so `idg([@PosInt.0, @Int.0])` is no longer refused where `idg([@Int.0, @PosInt.0])` is accepted, and `[pure_fn, io_fn]` is accepted as `[io_fn, pure_fn]` was.  An empty literal takes its type from its context, and an index expected at a type reads an array of that type, so `let @Int = [][0];` compiles where code generation skipped the function.  Spec §4.2, §4.8, §4.12.1, §5.9 and §11 state the rules.  An index no context types (`match [][0] { ... }`) is [#1862](https://github.com/aallan/vera/issues/1862)'s.
