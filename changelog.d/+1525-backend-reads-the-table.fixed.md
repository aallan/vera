- **A program whose types code generation re-derived compiles, loads and runs at the checker's types** (thirty checklist lines of [#1525](https://github.com/aallan/vera/issues/1525)).  Seventeen compiled with the function dropped (`E602`), so `vera run` refused to call it: a `let` or a binder at a parameterised alias (`let @Id<Nat> = 5`, `Some(@Id<Nat>)`, `let @Wrap<Int>`, `let @Two<Int>`), `apply_fn` on a closure a call returns or a `State` cell holds, an index into an array literal or into a generic call's array (`[true][0]`, `id([4, 5])[1]`, `pick([1, 2][@Nat.0], 5)`), a `match` on an `array_fold`, an integer pattern over a call returning `Byte`, an array literal of closures, a constructor of `array_map`'s result, `show` of `array_reverse`'s, and a literal or wildcard sub-pattern (`Some(3)`, `Tuple(@Int, _)`).  Six compiled to a module that did not load: a `@W<Int>` parameter for `type W<T> = String` (`expected a type but nothing on stack`), a `State<Future<Int>>` cell (`expected i32, found i64`), `wrap(3)[0]` for `forall<T> fn wrap(@T -> @Array<T>)` (`expected i64, found i32`), an `if` whose arms are a `throw` and an `array_fold`, or two `State` handlers (`values remaining on stack at end of block`), and a `let @Opt<Int>` that dropped `main` and left `option_unwrap_or$Int` behind (`unknown memory 0`).  Seven ran to a wrong value: `==` on two calls returning a data value compared heap addresses, so `mo(7) == mo(7)` and `wrap(1) == wrap(1)` were `false` and `same`'s `ensures(@Bool.result)` over `duo(7) == duo(7)` trapped; `map_get` on a `State<Map<String, Int>>` cell's value returned 0 for 5; `map_keys` of an `if` printed an empty line for `a`; `"\(byte_id(65))"` printed `true` for `A`; and `"\(-@Nat.0)"` trapped (`Negative value bound into a @Nat slot`) where it is `-5`.
- **A closure argument no longer carries a negative value into a `@Nat`** ([#1525](https://github.com/aallan/vera/issues/1525)).  `apply2(@Nat.0, fn(@Int -> @Int) effects(pure) { @Int.0 - 100 })` returned -95 from a `-> @Nat` function, and `array_fold(@Array<Int>.0, @Int.0, fn(@Nat, @Int -> @Nat) effects(pure) { @Nat.0 })` handed -7 to the closure's `@Nat` parameter, with `vera check` and `vera verify` clean.  Under the polarity rule (Changed, above) each is a narrowing the verifier records and code generation guards: `vera verify` refutes the second (`E503`), and both trap at run time rather than return a negative `@Nat`.
- **A refinement in an effect's type argument is type-checked as a refinement anywhere else is** ([#1525](https://github.com/aallan/vera/issues/1525)).  `effects(<Exn<{ @Int | @Int.0 + 1 }>>)` passed `vera check` with a predicate that is not a `Bool`, and its module did not load; it is refused with `E126` (`Refinement predicate must be Bool, found Int.`), in a signature's row, a function type's, a closure's and a handler's effect alike.  **Breaking** for such a predicate in a handler's or a closure's effect, which ran: write the predicate as a `Bool`.  No example, conformance program or documentation example has one.
