- **Breaking: every position that binds or passes a value at a written type holds the value to its type by subtyping, as a `let` does** ([#1896](https://github.com/aallan/vera/issues/1896)).  Three positions had a judge of their own.  A handler clause's parameter was compared with nothing: `throw(@String) -> { @String.0 + 1 }` under `handle[Exn<Int>]` checked, verified and added to an `Int`.  A `match` binder asked whether its type and the value's were related in either direction, and skipped a function-typed scrutinee and one holding a type variable: a binder at another function type trapped `indirect call type mismatch` after a clean verify, `@Option<Int>` over an `Option<T>` given `Some("abc")` returned 4, and `@Option<W>` over an `<IO>` function's `Option` ran IO from a `pure` function.  A call argument, a destructured component, an array element and a generic call's result taken at its expected type, whose pair holds a type variable, were fitted by the join, which compares an effect row inside a parameter's function type the wrong way round, so a `fn(@P, @T -> @Int)` closure, `P` pure, fitted `fn(I, T -> Int)` with `I` performing IO.  Each position now reads each type variable a call left open as unknown, keeps the enclosing function's own, and asks whether the value's type is a subtype of the written one (spec §2.8, §4.9.1, §5.9, §7.5.1).  A `@Nat` or refined binder over an `Int` stays a narrowing the verifier obligates (E503, `refine_bind`), a variable a call leaves open stays accepted (`match None { Some(@Int) -> ... }`), and no program in the examples, the conformance suite, the documents or the benchmark's solutions has any of the refused shapes.  A function type that fits only by a narrowing is E190, as before; any other misfit is the position's own refusal:
  - a clause parameter at a type the operation's value does not fit is the new **E342**, and the slot takes the type the clause writes: write the parameter at the type the operation takes (`throw(@Int)` under `Exn<Int>`), and bind another type with a `let` in the clause body where it fits;
  - a binder at a type the value's is not a subtype of is **E314**: a function type with other parameters, arity, result or a narrower effect row, a concrete type over a value typed by the function's own type parameter (`@Option<Int>` over `Option<T>`, `@Int` over `T`, `Tuple(@String, @Int)` over `Tuple<T, Int>`), the type parameter over a concrete type (`@T` over an `Int`) and `@Never` over any other type; bind the value at the scrutinee's type;
  - a constructor or literal pattern at a position whose type is the enclosing function's own type parameter, the scrutinee or a sub-pattern's (`Some(@Int)` over `@A.0`, `Some(None)` over an `Option<T>`, which drew E311 before) is **E314**: nothing says an `A` is an `Option`, and an instance at which the head matched read its field at whatever type the instance gave it (a `Bool` read as an `Int`, with every gate green); take the value at the type the pattern matches;
  - an argument, a component, an element or an adopted result with a parameter's effect row the wrong way round is **E202** at an argument and **E170** at a binding: write the closure at the position's type, with its parameters' effects.
- **Breaking: E542 is gone.**  It disclosed a `match` binder bound at a function type whose effect row is narrower than the value's (`effect_bind`, `tier3_unguarded`, since 0.2.7).  That binder is refused at check (E314), so no program reaches the row, and the row kind and the code are deleted.  A consumer that read E542 from `vera verify --json` reads E314 from `vera check --json` for the same program.
