- **A destructuring `let` is checked as the constructor pattern it names** ([#1545](https://github.com/aallan/vera/issues/1545)).  The checker bound each type a destructure writes as written and compared none of them with the value, so `let Tuple<@Int, @String> = Tuple(1, 2);` passed `vera check` and `vera verify` and `@String.0` read the integer 2 as a string; nor did it read the head, so `let Other<@Int, @Int> = Pair(1, 2)`, `let Some<@Int> = None`, `let Tuple<@Int, @String> = Tuple(1, "a", true)` and `let Tuple<@Int, @Int> = 5` checked clean and ran on whatever the bindings' layout read, or failed to load.  A destructure is now held to the rules of its one-arm `match`, through the functions that decide them for the arm, and each binding to a `let` binding's: the head names the value's type or one of its constructors (`E320` for neither, `E314` for another type's, and for `Tuple` over a tuple of another width), a data constructor has one binding per field (`E321`), a type with another constructor is taken apart by a `match` (`E311`), a type no constructor builds, a type parameter's among them, is not destructured (`E313`), and each component fits its binding as a call argument fits its parameter (`E170`), so a `@Nat` component widens into an `@Int` binding and an `@Int` one narrows into a `@Nat` or a refined binding with the verifier's obligation, as in a plain `let`.  The value's type is the one it synthesizes, never the bindings', so an `if` whose branches build `Tuple(1, 2)` is refused at a `@String` binding too.  The checker reads the head as the verifier already did.  `tests/test_destructure_checked_against_source_1545.py` holds the rule over 522 cells: six heads, six value forms, five relations of a component to its binding and three arities.
