- **A `Set` enumerates its elements in insertion order on every host and in every run.**  The native host enumerated a set in Python's set order, which for a `Set<String>` changes from one process to the next with Python's string hashing (three runs, three orders) and for a `Set<Int>` is neither insertion nor numeric order (40, 3, 17, 9 read back as 40, 17, 3, 9), while the browser runtime kept insertion order.
- **A `NaN` key inserted again keeps its position.**  The native host moved it to the end of `map_keys`, so a map built by inserting `NaN`, `1.0` and `NaN` read back `1.0, NaN` there and `NaN, 1.0` in the browser.
- **A `-0.0` key reads back as `0.0` on every host.**  `-0.0` and `0.0` were one key on both hosts, and the native host kept whichever came first, so `map_keys` of a map whose first zero key was `-0.0` read back `-0.0` there and `0.0` in the browser.
- **`json_parse` builds an object of any width whose members are not strings.**  The host rooted every member's value until the object's map was built, so an object of 4,100 members overflowed the shadow stack (`#692: host shadow-stack overflow`; in the browser, `GC shadow stack overflow`); the map is built from two rooted arrays now, and an object of 10,000 numbers parses on both hosts.  One of 10,000 strings still overflows ([#1733](https://github.com/aallan/vera/issues/1733)).
