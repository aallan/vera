- **A program's declarations and the compiler's own functions and exports are two namespaces** ([#1694](https://github.com/aallan/vera/issues/1694)).  Every declaration's WebAssembly function is named `$:` followed by its link name (`$:main`, `$:mod$util$helper` for `helper` in `module util;`, `$:f$where$h` for a `where` helper, `$:identity$Int` for a clone), and no function the compiler writes for itself (`$alloc`, `$gc_collect`, a lifted closure's `$anon_0`, a derived `$eq_Shape`) has a `:` in its name, so a user function named `alloc`, `gc_collect`, `anon_0` or `eq_String` beside a program that makes the compiler emit its own no longer fails to compile with a duplicate identifier ([#1494](https://github.com/aallan/vera/issues/1494)), and under `--target wasi-p2` a function named `wasi_tbl`, `wasi_arena_ptr` or `cabi_realloc` compiles instead of being refused as a reserved identifier.  **Breaking**: the compiled module exports its runtime under names that start with `vera.`, which no Vera identifier can spell: its linear memory as `vera.memory`, the allocator as `vera.alloc`, the GC globals as `vera.heap_ptr`, `vera.gc_sp` and `vera.gc_stack_limit`, and the wrapper registration as `vera.register_wrapper` (and the WASI 0.2 core module's adapter table, arena pointer and realloc as `vera.wasi_tbl`, `vera.wasi_arena_ptr` and `vera.cabi_realloc`), so a public function named `alloc` is exported as `alloc` beside the allocator.  The browser runtime's `getExports()` lists the program's own functions and none of the runtime's, `register_wrapper` included.  To upgrade, an embedder that read `memory`, `alloc`, `heap_ptr`, `gc_sp`, `gc_stack_limit` or `register_wrapper` from a compiled module's exports reads the `vera.`-prefixed name (`instance.exports["vera.memory"]`); a program's own exports keep their names.  The `vera compile --wat` text and a backtrace `wasmtime` prints itself name a declaration's function with its `:` (`Main!:handle`); Vera's own trap reports name it as declared.
- **Two modules' same-named data types are two types** ([#1694](https://github.com/aallan/vera/issues/1694)).  The checker types a module's data type by its declaration, as code generation compiles it, so a module's type and another module's or the entry file's type of the same name never unify.  **Breaking**: two modules that restate one layout under one name, with a value of one reaching code that expects the other (`bone(aone(6))`, with `liba`'s `aone(@Int -> @Shape)` and `libb`'s `bone(@Shape -> @Int)`), compiled since [#1317](https://github.com/aallan/vera/issues/1317) and are refused at check, with `E202` for an argument or `E314` for a pattern, by a message naming both owners (`liba.Shape`, `libb.Shape`).  To upgrade, declare the type once, in one module, and import it in the other.  The reverse moved too: an entry file that declares a type of a module type's name, and imports a function whose signature carries the module's type without calling it, was refused (`E623`) and compiles.
- **A slot name's type argument keeps its refinement's predicate** ([#1674](https://github.com/aallan/vera/issues/1674)).  A refinement in a type argument is rendered with its predicate, canonically, where it was rendered `{@Int | ...}`, so `@Array<{ @Int | @Int.0 > 0 }>` and `@Array<{ @Int | @Int.0 < 0 }>` are two slot names.  **Breaking**: two bindings whose types differ only in such a predicate are two stacks, each counted from `.0`, where they were one, and a reference to one writes the predicate as the binding's type does (`@Array<{ @Int | @Int.0 > 0 }>.0`).  To upgrade, a reference that reached the second of two such bindings as `.1` reaches it as `.0` of its own type; `vera check --explain-slots` prints each binding's slot name with its predicate.
