- **An `Exn` handler's value is the join of its handled body's and its `throw` clauses', and a clause whose value fits no join is refused with `E341`** ([#1794](https://github.com/aallan/vera/issues/1794)).  The checker typed a handler by its body alone and checked a clause's body against nothing, so a clause of another type passed `vera check` and `vera verify` and its value was read at the body's type: with `throw(@Int) -> { some_of(@Int.0) }` beside a body of type `Result<Int, Int>`, `pick(true)` printed `105`, the clause's `Some(5)` read as `Err(5)`, and an `Int` body beside a `Bool` clause compiled to a module that did not load (`type mismatch: expected i64, found i32`).  A body that always throws made the handler `Never`, which fits any type, so `handle[Exn<Int>] { throw(@Int) -> { @Int.0 + 1 } } in { throw(@Int.0) }` was accepted as the body of a `-> @String` function and its module did not load; the handler has its clause's type, so that body is refused with `E121`.  A `Nat` body beside an `Int` clause joins at `Int`, so a `let @Nat` of the handler is a narrowing the verifier records and code generation guards.  `E341` is reported at the clause's body (`The 'throw' clause's value has type Option<Int>, but the handler's value is Result<Int, Int>.`), with a fix that writes a value of the handler's type in its place (`replace 'some_of(@Int.0)' with 'Ok(0)'`).  A clause that throws again is `Never` and keeps the body's type, and a `State` handler is typed by its body as before.  **Breaking** for a program whose clause produces a value of another type than its handled body's, which `vera check` accepted: give the two one type, as the fix says.  No example, conformance program or documentation example has one.
