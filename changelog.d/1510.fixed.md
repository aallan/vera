- **The collector marks a heap of any width: a full mark worklist no longer traps** ([#1510](https://github.com/aallan/vera/issues/1510)).  `$gc_collect` marked through a worklist of 16,384 entries, and a push that found it full executed `unreachable`, so a correct program died in the collector whenever a collection ran with more values pending at once than that, in a heap it had already allocated.  The issue's 20,000-element `Array<String>` trapped inside `array_map`, and under ordinary collection so did an `Array<String>` of 16,385 strings, a list of a user `data` 16,384 cells long, an array of 16,385 boxed closures each capturing a `String`, and a string-keyed `Map` built by `map_insert` from 596 keys, natively, in the browser runtime and under `--target wasi-p2`.  A child push that finds the worklist full is now dropped and the object being scanned recorded as dirty: the lowest dirty object with the word its push was dropped at, and the highest.  Once the worklist empties, that range is walked along the allocation chain and each marked object in it scanned again, a walk that fills the worklist resuming where it stopped, until a drain drops nothing.  The worklist bounds the collector's memory, not the heap it marks, and the memory layout is unchanged.  The seed's push loses its capacity test, since it pushes at most one entry per shadow-stack root and the 4,096 roots always fit, and code generation refuses a layout whose worklist is smaller than its shadow stack.  The `unreachable` trap's Fix paragraph names four causes; the mark worklist is no longer one.
