- **Breaking: a type variable inside a function-typed argument is fixed by that argument's declared type, by the polarity of the position it holds** (spec §4.2, [#1525](https://github.com/aallan/vera/issues/1525)).  The first argument fixed a generic's variable and a closure was admitted at the other integer type, so with `forall<T> fn apply2(@T, @Endo<T> -> @T)`, `apply2(@Nat.0, fn(@Int -> @Int) effects(pure) { @Int.0 - 100 })` was a `@Nat` holding -95, and `apply2(@Int.0, fn(@Nat -> @Nat) effects(pure) { @Nat.0 })` handed -7 to the closure's `@Nat` parameter, with `vera check` and `vera verify` clean.  A declared `Int` at a position whose values the generic receives (the closure's return, a parameter of one of its parameters) now makes the variable `Int`, and a declared `Nat` at a position the generic fills (a parameter) makes it `Nat`, so the `Int` value argument is a narrowing where it enters, as in `pick(@Nat.0, @Int.0)`; `array_fold`, a user generic and a constructor take the rule alike.  A closure that fixes one variable both ways is refused at that argument with `E202`, which names the two positions and the two types, and whose fix declares the closure's `Int` result `Nat` (`replace 'fn(@Nat -> @Int)' with 'fn(@Nat -> @Nat)'`).  Upgrade: a `let @Nat`, a `@Nat` argument or a `@Nat` result of such a call, which was typed `Nat` and checked by nothing, is a narrowing, obligated by `vera verify` (Tier 3, or refuted with `E503`) and guarded where it is bound: declare the closure's result `@Nat`, or bind the call at `@Int`.  No example, conformance program or documentation example changes verdict.
- **Code generation reads every type from the typed program and derives none** ([#1525](https://github.com/aallan/vera/issues/1525)).  A value's width is its checked type's, and an `if`'s, a `match`'s and a handler's block result the join's (an `Exn` handler's the join of its body and its clauses, [#1794](https://github.com/aallan/vera/issues/1794)); a call's, an element's, a key's, a value's, a scrutinee's and an interpolated part's type is the checker's; a value declared at a written type (a `let`, a parameter, a binder, a cell, a payload) is laid out by the type that resolves to, a parameterised alias's target under its arguments, and a sub-pattern's field by the type it matches; and whether a value narrows into a `@Nat` slot is the verifier's rule (`vera.narrowing.nat_narrowing`) over the same types.  The 23 `_infer_*` walkers of `vera/wasm/`, code generation's `@Nat` reading by declared name, the `@Byte` literal marks and the fused-`await` predicates over syntax are deleted.  Over the 323 corpus programs, 44 compile to different WAT and none changes whether it compiles: 26 lose 65 `nat_guard` checks that could not fail, at the binding of a value the checker types `Nat` (a `@Nat` call, a `State<Nat>` operation, an alias of `Nat`), which code generation guarded by its own reading and the verifier recorded no narrowing for, and six of them no longer import `vera.trap`; 17 root a heap value a call returns that code generation could not type and left off the shadow stack (39 pushes), or save the shadow stack's top around an `Exn` handler; and 3 lose a `drop` after a `throw` statement.
- **A built-in's type variable is bound through a refinement alias of its argument's type** (the [#1688](https://github.com/aallan/vera/issues/1688) line of [#1684](https://github.com/aallan/vera/issues/1684)).  `map_values(@M.0)`, for `type M = { @Map<String, String> | map_size(@Map<String, String>.0) >= 0 }`, left its value variable unbound, so the element fitted any parameter: `takes(map_values(@M.0)[0])`, with `takes(@Nat -> @Nat)`, passed `vera check` and compiled to a module that did not load.  The variable is bound from the refinement's base, so that call is refused with `E202` (`Argument 0 of 'takes' has type String, expected Nat.`), and at a `@String` parameter it runs as before.
