- A tail-recursive function with a postcondition or a refined return type keeps its self tail calls, so a loop over a scalar measure runs at constant stack depth ([#1851](https://github.com/aallan/vera/issues/1851)).  An `ensures` that is compiled into a check (every one but a non-trivial `ensures` on a function returning a `String` or an `Array`, spec §11.8) is checked where a function returns to its caller: a function with a check after its body that calls itself in tail position compiles as an entry, which calls the body once and runs the check on what it returns, and a body, whose self tail calls transfer to the body.  `count_proved`, whose `ensures(@Nat.result >= 0)` is proved, exhausted the call stack at 50,000 steps and now runs a million, as its `ensures(true)` twin does; a loop whose postcondition is checked at run time, a refined return, `old` and `new` state, a `where` helper and a loop that allocates on every hop do too.  Preconditions, refined parameters and the `decreases` measure are still checked on every hop, and a self call that is not in tail position is checked when it returns.  What is given up: a step inside the loop whose own instance of the postcondition fails no longer traps when the loop's answer satisfies the postcondition at the caller's arguments; a direct call at that step's arguments still does.  Mutual recursion stays bounded by the call stack.  Spec §6.2.2 and §11.8.3 state the rule.
- A generic function's self-recursive tail call transfers ([#1525](https://github.com/aallan/vera/issues/1525)): a clone's call still names the generic, and code generation, which recognised a function's own call by its name, compiled it as a plain call, so a generic counting loop exhausted the call stack at a million steps where its non-generic twin ran.  One predicate now names a self tail call, resolved through the typed program, for the obligation table and code generation alike: the measure is checked at the call and the call transfers, under `ensures(true)` and under a postcondition.
- The `stack_exhausted` trap's Fix paragraph says what still costs a tail call.  It no longer names a postcondition or a refined return type, and it names what still compiles a call in tail position to a plain `call`: a guard on the call's result where it becomes a type with a `Nat` component, a tail call between two functions that recurse through each other under `decreases`, and a tail call of another function from a function with a postcondition that never calls itself in tail position.  It also names a second source of the trap: the run-time guard of a `decreases` over a data type walks the structure at every recursive call, so the paragraph advises measuring such a loop by a `Nat` it carries, and offers writing the loop as one function calling itself beside keeping the recursion's depth inside the engine's call stack.
- Spec §5.6.1 states what a measure costs: guarded iteration over a scalar measure runs at constant stack depth, and an ADT measure is ranked at each hop, at a cost and stack depth proportional to the structure it ranks.
- Spec §11.8.4 states `old` and `new` for a function compiled as an entry and a body: the entry takes the `old(State<T>)` snapshot before it calls the body and reads `new(State<T>)` after the body returns, so `old` is the state when the caller called and `new` the state when the function returns to it.
