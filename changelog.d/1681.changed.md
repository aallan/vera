- **An effect row code generation cannot lower is refused at check, at the row entry** ([#1681](https://github.com/aallan/vera/issues/1681)).  A function whose row named a user-declared effect, or `State` or `Exn` without a type argument, passed `vera check` and `vera verify`, and code generation dropped it (E603, E606, E611).  Rule 6 in `vera/lowering.py` refuses each such entry with E340, in every row: a function's, a `where` helper's, a closure literal's and a function type's.  A closure or a function type whose row named a user-declared effect compiled, and nothing could apply it, since applying it needs the effect in the caller's row.  So a user-declared effect is a declaration only: the `effect` block checks, and a handler for one was already refused (E340).  Code generation's own refusal is an internal error (E699) that no checked program reaches.  `tests/test_lowering_boundary.py` holds the rule over 14 kinds of row entry (the registry's eight built-in effects without a type parameter, `State<Int>`, `Exn<Int>`, `State`, `Exn`, a user-declared effect, and one beside `IO`) in five places (a function's row, a `where` helper's, a constrained generic's, a closure literal's and a function type's).
  - `examples/effect_handler.vera` counts with a `State<Int>` row in place of its user-declared `Counter`, and `examples/maximum_syntax.vera` keeps its `Counter` and `Logger<T>` declarations and drops the two functions whose rows named them.
  - Spec §7.2, §7.3 and §11.4.1, SKILL.md and ROADMAP.md state the rule, and spec §6.4.3 and §11.17 and SKILL.md say a user-declared effect operation's argument is unreached because its row is refused at check.  DESIGN.md's effects paragraph no longer says user-defined effects follow the built-in effects' pattern.
