- **An effect row code generation cannot lower is refused at check, at the row entry, and so is a call of a user-declared effect's operation** ([#1681](https://github.com/aallan/vera/issues/1681)).  A function whose row named a user-declared effect, `State` or `Exn` without a type argument, or a row variable (`forall<E>` with `effects(<E>)`), passed `vera check` and `vera verify`, and code generation dropped it (E603, E606, E611), for a row variable the template and every clone.  Rule 6 in `vera/lowering.py` refuses each such entry with E340: a user-declared effect and `State` or `Exn` without a type argument in every row (a function's, a `where` helper's, a closure literal's and a function type's), and a row variable in a function's own row, since code generation compiles each instantiation's types and never its row.  A row variable in a function type's row, a parameter's or a closure literal's, compiled and still does.  A closure or a function type whose row named a user-declared effect compiled, and nothing could apply it, since applying it needs the effect in the caller's row.  An operation of a user-declared effect called where no row names it, `Counter.tick(())` in an `effects(<IO>)` function, in a closure whose row is a row variable or in a refinement predicate, passed check and verify and compiled to a module that does not load; it is refused at the call (E340), and that is the call's one refusal: the purity check (E122) does not count it.  So a user-declared effect is a declaration only: the `effect` block checks, and nothing that uses it does; a handler for one was already refused (E340).  Code generation's own refusal of a row entry is an internal error (E699) that no checked program reaches.  A function whose own row names a row variable and that nothing calls ran at the base as dead code, the function dropped, and is refused now.  `tests/test_lowering_boundary.py` holds the rule over 16 kinds of row entry (the registry's eight built-in effects without a type parameter, `State<Int>`, `Exn<Int>`, `State`, `Exn`, a user-declared effect, a row variable, and each of the last two beside `IO`) in five places (a function's row, a `where` helper's, a constrained generic's, a closure literal's and a function type's), over an operation performed in a closure whose row is a row variable (a user-declared and a built-in operation, applied and not, under a pure and an `<IO>` row), and over one in a refinement predicate (an alias's, a data field's, a signature's and a `where` helper's).
  - `examples/effect_handler.vera` counts with a `State<Int>` row in place of its user-declared `Counter`, and `examples/maximum_syntax.vera` keeps its `Counter` and `Logger<T>` declarations and drops the two functions whose rows named them.
