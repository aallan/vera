- **A refined or `Nat` value produced inside a `handle` is checked where the same value is checked outside one, and a `get` clause's `resume` argument is held to its cell's refinement** ([#1542](https://github.com/aallan/vera/issues/1542)).  The obligation table listed every row below a `handle`'s value (its body's, or a non-resuming `Exn` clause's) as one no run-time check guards, so `Some(float_to_int(@Float64.0))` built as a `State` handle's value at `Option<PosInt>` returned a negative payload with `vera verify` disclosing it (`E506`), and a `Tuple<Nat, Int>` produced there returned -5 (`E504`).  Code generation checks a construction by its own row and a closure argument at its leaves, inside a handle as outside, so those rows are now checks and the run traps.  The `Nat` requirement was not handed into a handle at all: `Some(sc(@Int.0))` built there at `Option<Nat>` was listed nowhere, verified clean and returned -5; it is now checked.  A `get` clause's `resume(x)` at a refined cell (`State<Pos>`, `State<{ @Set<Int> | set_size(@Set<Int>.0) > 0 }>`) ran the `Nat` sign guard and not the refinement's predicate, so `vera verify` refused the program (`E541`), and `vera run` returned -5 at `State<Pos>` and let the empty set through at the `Set` cell; it now takes the predicate's check, as the initial value, `put`'s argument and a `with` override do, and traps (`Refinement violation in State get resume`).
- **Breaking: a `handle`'s value bound by a `let` at a tuple type whose component is refined outside the solver is refused (`E541`), where it was accepted with a warning (`E506`)** ([#1542](https://github.com/aallan/vera/issues/1542)).  `let @Tuple<Short, Int> = handle[State<Bool>](...) { ... } in { mk(@Int.0) }`, with `type Short = { @Int | string_length(to_string(@Int.0)) < 3 }` and `mk` returning a `Tuple<Int, Int>`, gets the verdict the same value has at a `let` written directly: the row is listed as checked and no boundary decomposes a tuple at a `let`, so `vera verify` exits 1 where it exited 0.  The same holds for an `Exn` handle's value at a tuple component the solver decides (`{ @Int | @Int.0 < 10 }`), which the verifier does not decide there.  The run is unchanged.  A tuple component refined outside the solver stays unchecked inside a `handle` as at a `let`: this is the part of [#1542](https://github.com/aallan/vera/issues/1542) that stays open; bind the component at its refined type with a `let` (`let Tuple<@Int, @Int> = mk(@Int.0); let @Short = @Int.1;`) and build the tuple from the slot, which is checked.
