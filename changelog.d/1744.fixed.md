- **A module declares the `State` cells and `Exn` tags its emitted code uses, and an `Exn` handler's block declares the result its arms leave** ([#1744](https://github.com/aallan/vera/issues/1744)).  Each emitter that calls a cell (a handler's push, put and pop, a `get` or a `put`, an inlined clause, an `old` snapshot, a `new` read) or throws or catches a tag (a `throw`, a handler, an export's boundary) records it on its function's context, and the record joins the module's at the merges the host imports' records join it at, so a function code generation drops (`E602`) declares neither.  With a `handle[State<Int>]` or an `effects(<State<Int>>)` row in a dropped function, the module declared `state_get_Int`, `state_put_Int`, `state_push_Int` and `state_pop_Int` with nothing calling them, and `--target wasi-p2` refused it (`state (Int)`).  A cell a row names and no code calls is not declared either, so `ExecuteResult.state` holds an entry for each cell the code calls.  An `Exn` handler's block takes its result from the type the checker gave the handler, or from its `throw` clause's where the handled body always throws.  It took it from code generation's own reading of the two arms, which had no answer for an arm ending in a handler or in an `array_fold` over a closure, so an `Exn` handler with a `State` handler in its body and in its `throw` clause compiled to a module that did not load (`values remaining on stack at end of block`).  `_scan_io_ops`, whose walk reached only what the handler walk reaches, is deleted; the handler walk refuses a function whose handler names a cell or payload no lowering exists for (`E607`, `E612`) and declares nothing.  Of the 458 corpus and documentation programs that compile, one moved: `tests/conformance/ch07_state_new_family.vera` declares its cells in the order its code first uses them, with the same imports and the same output.
