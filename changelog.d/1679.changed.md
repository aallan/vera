- **Generics are monomorphized once, after the check, and the verifier and code generation read the same instances** ([#1679](https://github.com/aallan/vera/issues/1679)).  The checker records each generic call's type arguments by the call's identity, and `vera.typed` derives the instances a program needs from those records, transitively through each instance's own generic calls, links the program once and builds each clone once, every node of it with an identity and a type of its own; each generic call names the instance it calls.  The verifier and code generation each ran a discovery of their own, from the AST, and the two sets differed.  **Breaking** for a program that names a clone: a clone is named by its type arguments with their arguments, at the instantiation the checker inferred, so a runtime contract message, a backtrace frame and an exported clone spell it so: `gid$Box_LInt_R(@Box<Int> -> @Box<Int>)` where it was `gid$Box(@Box -> @Box)`, and `option_unwrap_or$Nat` where a call's result is bound at `@Nat`, where it was `$Int`.  Over the 323 corpus programs, 7 compile to different WAT: one by a clone's name alone, four losing `nat_guard` checks that could not fail (a clone's `Nat` result read back at `@Nat`, a built-in's `Nat` result, a type-parameter field the scrutinee's type holds at `Nat`), one checking `gid`'s `ensures(@T.result == @T.0)` at `Box<Int>` by structure where it compared heap addresses, and one building two clones where one clone, named at a truncated type, served `List<List<Int>>` and `List<List<List<Int>>>`.
- **`verify`, `compile` and `test` take the typed program as their one input (breaking, for a program that calls them).**  `vera.verifier.verify(typed, source, file, timeout_ms)`, `vera.codegen.compile(typed, source, file)` and `vera.tester.test(typed, source, file, ...)` read every type, instantiation and clone from `typed`, which `vera.typed.build(program, resolved_modules, artifacts)` makes from `typecheck_with_artifacts`'s artifacts after a check that reports no error; the optional table parameters (`expr_types`, `expr_semantic_types`, `expr_target_types`, `module_artifacts`) and the fallbacks that re-derived a table nobody passed are gone, and a program the check refuses has no typed program.  The `vera` commands are unchanged.
- **A program whose generic instances would grow without bound is refused at check, with `E139`** ([#1679](https://github.com/aallan/vera/issues/1679)).  A cycle of generic calls that instantiates one of its generics at a type larger than the variable it holds, `f<T>` calling `g` at `Option<T>` and `g<U>` calling `f` at `Option<U>`, needs an instance at a larger type for every instance.  Code generation served every depth with one clone whose name dropped the type's argument (`f$Option`), which ran only because every depth had the same representation.  Each call that grows the cycle is refused at the call, naming the cycle (`f<T> -> g<Option<T>> -> f<Option<Option<T>>> -> ...`), with a fix that passes the caller's type variable itself, as a data declaration whose recursion is not regular is refused (`E129`).  **Breaking** for a program holding such a cycle, which `vera check` accepted: pass the type variable unchanged at each call the diagnostic names, or carry the nesting in a value of a recursive data type.  No example, conformance program or documentation example holds one.
