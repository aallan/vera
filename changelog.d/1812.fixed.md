- The type a context names reaches every construct that types a value ([#1812](https://github.com/aallan/vera/issues/1812)).  A value that leaves a type variable open (`None`, `[]`, `Ok(1)`, a generic call no argument of which fixes its variable, an index over an empty literal) took the type its position names only where a check listed the kind of value it repaired.  An `Exn` handler's body and clauses, an array literal's element, a tuple's component, a generic call's argument, an ability operation's argument, a field of a data type with no type parameters, a binding that held a literal beside a nested call's open variable, and a `match` scrutinee whose binding pattern names its type each missed some: the program was refused (`E121`, `E170`, `E164`, `E213`, `E241`, `E613`), or `vera check` accepted it and code generation dropped the function that held it (`let @Array<Int> = array_reverse([]);`: `E602` at `vera verify`, `E907` at `vera run`), or the check accepted it with the variable left open in the types and instances it recorded.  Each of these now takes the type its context names (spec §5.9): a handler under a function returning `Result<Int, String>` whose body is `Ok(1)` and whose clause is `Ok(0)` checks, as an `if` of the same values did, and so do `let @Int = idg([][0])`, `Box([][0])`, `compare(head_ord([]), 5)`, `idg(Tuple(head_ord([]), 1))` at a `Tuple<Int, Int>` and `match none_ord(()) { @Option<Int> -> 0 }`.  An ability operation's two arguments that each leave the other's variable open (`eq(Ok(1), Err("e"))`) are still refused.  No program that checked is refused.
