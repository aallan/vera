- **Bytes in, out and through: `IO.read_bytes`, `IO.write_bytes`, `string_to_bytes`, `bytes_to_string`, `base64_encode_bytes` and `base64_decode_bytes`** ([#1711](https://github.com/aallan/vera/issues/1711)).  A file whose bytes are not UTF-8 could not be read, nothing wrote bytes, and `base64_decode` returned a `String`.  `IO.read_bytes : String -> Result<Array<Byte>, String>` and `IO.write_bytes : String, Array<Byte> -> Result<Unit, String>` move a file's bytes unchanged, with no decoding and no newline translation, on the native host and in the WASI command world; the browser runtime refuses both as it refuses `IO.read_file`, and `--target wasi-p2 --world server` refuses both at compile, naming `wasi:filesystem`.  `string_to_bytes` gives a string's UTF-8 bytes, and `bytes_to_string` decodes bytes to a string, with `Err("invalid UTF-8 at byte N")` naming the offset of the first byte of the first sequence that is not well-formed UTF-8.  `base64_encode_bytes` and `base64_decode_bytes` are RFC 4648 Base64 over `Array<Byte>`.  The four conversions are compiled in place, so the Python host, the browser runtime and both WASI worlds run the same code for them.  An `Array<Byte>` holds one byte per element in generated code, so a 3,000,000-byte file read whole is a 3,000,000-byte array.
