- **`vera verify` no longer refuses a correct program for a run-time check the module was never meant to hold** ([#1861](https://github.com/aallan/vera/issues/1861)).  The obligation table listed a check where code generation emits none, so the join with the compiled module reported `E541` on a program whose every obligation was discharged.  A value built in place (an array literal, `set_add`, `map_insert`, `set_new()`) at a refined collection type as a function's result, a block's last expression, or an `if` or `match` arm, at a return or a `let`, is now checked once, where the value reaches its position, so a function returning `[@Int.0]` as `{ @Array<Int> | array_length(@Array<Int>.0) > 0 }` verifies and its return is checked at run time.  An array literal or a join passed to a closure is checked as any closure argument is (below), and a join stored in a constructor field whose refinement is not over a scalar is disclosed (`E506`), as the same value stored directly is.  The workaround of binding the value with a `let` first is no longer needed.
- **An argument passed to a function value is checked at the call, against the function type's refined parameter** ([#1861](https://github.com/aallan/vera/issues/1861)).  Spec §6.7 has the compiler verify such an argument at the call site; where the solver could neither prove nor refute it, the run-time check was left to the entry of the closure that runs.  For a function operand that was not a slot reference (`apply_fn(if @Bool.0 then { @F.0 } else { @F.1 }, @Int.0)`, a `match`, a call's result, an index) no check stood anywhere, and `vera verify` refused the program (`E541`), including the overflow checks of a predicate such as `{ @Int | @Int.0 * @Int.0 * @Int.0 < 1000 }`.  For a slot, a closure that declares a wider parameter than its type, a `fn(@Int -> @Int)` bound at `fn(Pos -> Int)` (spec §2.8 rule 5), checks nothing at its entry, so `-5` reached it with `vera verify` reporting a run-time check (`E506`) ([#1885](https://github.com/aallan/vera/issues/1885)).  The check now stands at the call for every form of the function value and traps there (`Refinement violation in closure argument`); a closure that declares the refined parameter itself checks it again at its entry.  The argument's refined tuple components are checked at the call as well (`Refinement violation in closure argument (tuple component)`), and each refinement is checked as the program writes it, so a refinement over function values (`{ @Array<F> | … }` with `F` a function type) or over an alias (`{ @Count | @Count.0 > 0 }`) is checked where code generation would stop with an internal error; a refinement a generic alias writes over its own type parameter (`{ @Array<T> | … }`), and a payload or element below the argument, are disclosed (`E506`).  A program that passes such an argument runs one more predicate check per call.
- **A tuple component below a value stored in a constructor field or an array element is disclosed, not claimed** ([#1861](https://github.com/aallan/vera/issues/1861)).  `Tuple(pair(x), 0)` at `Tuple<Tuple<Short, Int>, Int>` listed the inner component's check, which the store does not make, so `vera verify` refused the program (`E541`); the component is now disclosed (`E506`).
- **`set_add`'s element and `map_insert`'s key are checked against a refined element type** ([#1861](https://github.com/aallan/vera/issues/1861)).  `let @Set<Pos> = set_add(set_new(), @Int.0)` and `let @Map<Pos, Int> = map_insert(map_new(), @Int.0, 1)`, with `type Pos = { @Int | @Int.0 > 0 }`, were refused by `vera verify` (`E541`), and `vera verify --no-reconcile` passed a module that stored -5; the element and the key now take the refinement's check, as an array literal's element and `map_insert`'s value do, and trap at -5.  The check binds the refinement as the program writes it, so one written over an alias (`type Count = Int; type PosCount = { @Count | @Count.0 > 0 }`) is checked too.
