- **A construction of a type its function names nowhere is modelled, whatever file declares the type** (the constructed-sort lines of [#1525](https://github.com/aallan/vera/issues/1525)).  `four(Bravo(@Int.0))`, in a function that names no `Gauge`, did not translate, so `four`'s `ensures(@Nat.result == 4)` was not assumed: a caller's `ensures(@Nat.result == 4)` over it fell to a runtime check (`E522`), and `pos(@Int.0)` after `let @Int = four(Bravo(@Int.0))` was refused with `E501`, where the same call after an unused `let @Gauge` proved.  A constructor of a data type the entry imports had no sort in the entry: `need(@Int.0)` after `let @Int = zero(Amber(0))` was refused with `E501`, and after `let @Tally = Amber(0)` and `let @Int = zero(@Tally.0)` it fell to a runtime check (`E532`).  Each proves at Tier 1 now, and so does an imported generic's `decreases` measure over its module's data type in the importer's run, as in the module's (the [#1577](https://github.com/aallan/vera/issues/1577) line of [#1561](https://github.com/aallan/vera/issues/1561)).
- **A value built from `@Nat` components and matched back at `Int` no longer crashes `vera verify`** (the [#1594](https://github.com/aallan/vera/issues/1594) line of [#1525](https://github.com/aallan/vera/issues/1525)).  `let @Option<Tuple<Int, Int>> = Some(Tuple(@Nat.0, @Nat.0))` matched with a `None -> Tuple(1, 1)` arm raised an internal error (`E699`, a Z3 sort mismatch); it verifies.
- **A counterexample names each parameter as the source does** (the [#1767](https://github.com/aallan/vera/issues/1767) line of [#1525](https://github.com/aallan/vera/issues/1525)).  For `private fn foo(@Int, @Int -> @Int)` with `requires(@Int.1 == 3 && @Int.0 == 4)`, `E500` printed `@Int.0 = 3` and `@Int.1 = 4`, the reverse of the `requires`; it prints `@Int.0 = 4` and `@Int.1 = 3`, and an instance of a generic names its parameters as the generic does (`@T.0`).
