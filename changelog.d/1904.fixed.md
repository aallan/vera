- **A module path names one file in a program, and a file is one module under one path: a program that breaks either is refused, with `E014` or `E015`** ([#1904](https://github.com/aallan/vera/issues/1904)).  The resolver looked an import up by its path in a cache before it looked for the importer's own file, so the first import of a path decided the file for every importer: with `lib.vera` and `a/lib.vera` both on disk, and `a/mid.vera` importing `lib`, `vera run` printed `22` when `main.vera` imported `a.mid` before `lib` and `11` when it imported `lib` first, where each import's own lookup (spec §8.6.1) gives `12`, and `vera check` and `vera verify` were clean.  And a file imported by two paths (`a.lib` from `main.vera`, `lib` from `a/mid.vera`) was read, checked and compiled twice, as two modules: two copies of each of its functions, and each data type it declares split in two, so a value built through one path was refused where the other path's type was expected (`E202`, "has type lib.Box, expected a.lib.Box").  Each import is now looked up from its own importing file, and spec §8.6.2 states the rule every later stage links by: a path names one file in a program, and a file is one module, under one path.  An import that finds another file for a path the program has already bound is `E014`, naming the path, both files and both importers, with a fix that renames one file and its import; an import that reaches, by another path, a file the program already imports is `E015`, naming the file, both paths and both importers, with a fix that writes the one path that reaches the file from both importers, where there is one.  Whether two names are one file is the filesystem's answer (`os.stat`'s device and file number, as `os.path.samefile` decides it), so a symbolic link, a hard link and, on a filesystem that ignores case, a spelling that differs only in case are the file they name.  Whether a program is refused does not depend on the order its imports are resolved in, and a program with one conflict gets the same code in either order; in a program with more than one, the order decides which import is named first and which of the conflicts are reported (`E014`, `E015` or both), since a refused import binds nothing and is not read, and each import a diagnostic names is a real conflict.  **Breaking** for three shapes of program that ran, each by the cache's accident: one path naming two files is `E014` (give one of the two modules another path, as the fix says); one file under two paths is `E015` (import it by one path everywhere, as the fix says); and an import whose own lookup finds no file is `E012`, where it was handed the module another import of the same path had found (write the path that reaches the module from that importer, or put the module where its lookup finds it).  No example, conformance program, documentation example or `vera-bench` program has any of the three.
- A cycle through two spellings of one file is `E011` at the import that re-enters the file, before the file is read a second time: the resolver tracks the files in progress, not the paths ([#1904](https://github.com/aallan/vera/issues/1904)).
- A module that is not UTF-8 is read and reported once (`E024`), however many imports reach it; it was reported once per importer ([#1904](https://github.com/aallan/vera/issues/1904)).  `E012` and `E013` stay one per failing import, at each import.
