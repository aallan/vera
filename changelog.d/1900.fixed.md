- A module whose only contact with the heap is a read of a parameter declares its memory, and loads ([#1900](https://github.com/aallan/vera/issues/1900)).  A function whose body matched an `Option`, a `Result` or a `Tuple` parameter, compared two `Option` parameters with `==`, or called a private function that did, compiled to loads from a memory the module never declared, when nothing else in the module allocated or held a string: `vera check`, `vera verify` and `vera compile` passed, and the module failed at load (`unknown memory 0`), in `vera run`, in the browser bundle and for any embedder.  The memory is now declared from the module's own instructions where it is assembled.  Three documented examples had the shape: `unwrap_or` in `SKILL.md`, `split` in `DE_BRUIJN.md` and `unwrap` in spec §3.8.1.
- Every module the compiler builds is validated before it is written ([#1900](https://github.com/aallan/vera/issues/1900)).  `wasmtime.wat2wasm` assembles text without validating it, so a module that does not load was written with exit 0.  The core module is now validated after assembly, and the `--target wasi-p2` component (both worlds) where it is built; one that does not validate is an internal compiler error (`E699`) naming the validator's message and, where it names one, the function, and no file is written.  `vera verify`, which compiles the program for its reconciliation, reports the same `E699`.
