- An expression a message quotes is the expression the program holds, written as `vera fmt` writes it ([#1573](https://github.com/aallan/vera/issues/1573)).  Every trap message, refinement guard, `vera run`'s `requires(...) failed` and `ensures(...) failed`, every obligation description in `vera verify --json` and every verifier diagnostic printed an operand without the parentheses its precedence needs, so `@Nat.1 - (@Nat.0 - 1)` read as `@Nat.1 - @Nat.0 - 1`, `requires((@Int.0 + 1) * 2 > 4)` as `@Int.0 + 1 * 2 > 4`, and E501's "At this call site" line named an instance that was true for a precondition the verifier refuted.  The same text now spells a `match`, an `if`, a block, a constructor or a qualified call where it printed `<expr>`, a quantifier's predicate where it printed `...`, a string literal with its escapes, and a small or large float positionally where it printed `1.847e-05`.  A suggested clause the message composes, such as a `requires` to add or an index's bounds, is built from the operands and written the same way.
- A refinement at a handler clause's binder is checked when it differs from the operation's payload refinement only by parentheses, or by a `match`, `if` or constructor in its predicate ([#1573](https://github.com/aallan/vera/issues/1573)).  The narrowing decision compared the two refinements by their rendered predicates, which the old renderer wrote alike, so `throw(@Tight)` under `handle[Exn<Loose>]`, with `Loose = { @Int | (@Int.0 + 1) * 2 > 4 }` and `Tight = { @Int | @Int.0 + 1 * 2 > 4 }`, bound 2 into `@Tight` with no obligation and no guard.  The binder now carries a `refine_bind` row (`E506` when it is checked at run time) and the guard traps.
- A diagnostic quotes the source line its location names when the line before it holds one of U+000B, U+000C, U+001C to U+001E, U+0085, U+2028 or U+2029 ([#1853](https://github.com/aallan/vera/issues/1853)).  The lexer reads those characters inside a line and counts lines by the newline, while the quoted line was cut at each of them too, so it was the wrong line or none.  Every reader of a source line (the parser, checker, verifier, code generation, module resolver, reconciliation, `vera test` and the language server's column transcoding) now cuts at the newline alone.
- The `stack_exhausted` trap's Fix paragraph states what the compiler does ([#1851](https://github.com/aallan/vera/issues/1851)): a call in tail position compiles to a plain call when something is checked after it returns (a postcondition the compiled code checks at run time, the guard of a refined return type, or the guard on the call's result where it becomes a type with a `Nat` component), and `vera verify` proving the postcondition or the refinement does not by itself remove the check.  It named only a postcondition left to run time and advised making it provable, which leaves the tail calls as they were.
