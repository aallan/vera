- **A `Map`'s or `Set`'s `String` keys hash under a key drawn for each instantiation** ([#1736](https://github.com/aallan/vera/issues/1736)).  The trie hashed a `String` key by FNV-1a over its bytes through a bijective mixer, with no key, so `String` keys chosen to share a hash shared one collision node, which every operation searches and copies whole: a program that builds a map from keys an adversary chooses, such as the request headers `vera serve` builds into a `Request` or the members of a JSON text it parses, paid O(n) per insert on such keys, 4,000 of them taking 1.25 s natively against 9.0 ms.  A `String` key now hashes by SipHash-1-3 over its UTF-8 bytes under a 128-bit key the module draws on its first `String` hash, two 64-bit words through the new `hash_key` host import: from `os.urandom` under `vera run` and `vera serve`, from `crypto.getRandomValues` in the browser runtime, and from `wasi:random` in a WASI component, which stock `wasmtime run` and `wasmtime serve` provide.  The key enters the hash's state, so keys that collide under one instantiation's key do not under another's.  No output depends on the key: the enumerations read insertion order, and the `Hash` ability's `hash` of a `String` is still the deterministic FNV-1a.  With the keyed hash, 4,000 inserts take 7.6 ms natively and 10.4 ms in the browser runtime, against 9.0 ms and 9.7 ms before; every other key type hashes as before, and its module draws no key.
  - A host other than Vera's own that runs a compiled core module binds `vera.hash_key` for a module that declares it: no parameters, one `i64` result, a fresh random word at each call.
