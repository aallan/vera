- **An effect operation is held to the effect row in force, wherever it is performed** ([#1702](https://github.com/aallan/vera/issues/1702)).  A call to a function was held to the row in force at the call (`E125`), and an operation of a built-in effect was compared with its row only when the row was `pure` (`E122`), so `effects(<IO>)` performing `Random.random_int(3, 3)` passed check and verify and ran.  So did `IO.print` in a `handle[State<Int>]` body inside a `pure` function, a `Random` operation in a `requires` clause or a `where` helper's body under `<IO>`, and a bare `throw` under `<IO>`, which code generation then dropped.  A closure literal's body was checked under the row around it, so the closure's own row held none of its operations: a closure declared `effects(<E>)` performing `Random` inside an `<IO>` function ran, and one declared `effects(pure)` performing `Random` inside a `<Random>` function was given a `pure` type.  An operation is now permitted where the row in force names its effect, at any instance of it (`<State<Int>>` permits `put`), and a row variable names no effect, so `<IO, E>` permits `IO`'s operations and no others; elsewhere the call is refused `E125`, or under `effects(pure)` the function `E122`, as before, with no second code at the call.  A closure's body is checked under the closure's own row, and a `pure` closure that performs an effect is refused `E122` at the closure.  Where the row in force is `pure`, a closure that performs an effect, directly or through a closure written in it, is still refused `E122`, at the function or closure it is written in, whether or not it is applied, and wherever a closure is applied the row in force must permit the closure's row (`E125`).  A handler's body is checked under the row around it with the handled effect added, as before.  A quantifier applies its predicate, a closure literal code generation inlines, where it is written, so it is held to the predicate's row as `apply_fn` is (`E125`, its effects counted for the purity check): a `pure` function whose `forall` predicate performs `IO` is refused at the quantifier (`E125`) as well as at the function (`E122`), and one whose row names `Random` and not the predicate's `IO`, which passed check before, at the quantifier.  A function's signature, a `where` helper's included, is checked where no row is in force, as a top-level one always was.  **Upgrading:** a program that performed a built-in effect's operation under a row that did not name the effect now fails check with `E125`: add the effect to the effects clause of the function or closure that performs it, as the diagnostic's fix writes it.
- **A `State` or `Exn` operation in a closure's body is refused at check unless a handler for its effect is written inside the closure** ([#1702](https://github.com/aallan/vera/issues/1702)).  Code generation compiles a closure as a function of its own, which registers no cell or tag from its row, so such a closure passed check and its function was then lost at compile: bare `put` and `throw` with `E602`, qualified `State.put` and `Exn.throw` with a module that did not assemble.  `vera.lowering` rule 7 refuses the operation at the call (`E340`), the call's one refusal.  A handler written inside the closure lowers it, and a handler around the closure does not, since the closure can be applied outside it; a quantifier's predicate, compiled into the function around it, is not read by the rule.  `tests/test_operation_row_1702.py` holds both rules: 502 cells over each built-in effect's operation, `put` and `throw` bare and qualified, under the rows `pure`, one naming the effect, one naming another and one naming both (and, for a closure, an open row naming either), at a function's body, a `let` initialiser, an `if` arm, a `match` arm, a `where` helper's body, a handler's body for the effect and for another, a handler's clause, a closure inside a `pure` function, one naming the effect and one naming another, a closure inside a handler for the effect, and a closure with that handler written inside it, and 108 over a quantifier's predicate at each declared row under a function whose row is `pure`, names the effect or names both.  309 of the 610 cells are red at fa958730, each a refusal the base did not make or made elsewhere; the 227 accepted cells check with no diagnostic and verify with every obligation proved, the 38 accepted closures compile and run, and the 27 accepted quantifiers compile.  The eight closure cells `tests/test_lowering_boundary.py` held accepted under `<IO>`, or refused at the function, are now refused at the call.
