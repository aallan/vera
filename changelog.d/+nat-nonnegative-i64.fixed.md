- **A `@Nat` is never read as a negative number** ([#1504](https://github.com/aallan/vera/issues/1504), [#1590](https://github.com/aallan/vera/issues/1590), [#1592](https://github.com/aallan/vera/issues/1592), [#1628](https://github.com/aallan/vera/issues/1628)).  Comparison, `/`, `%`, negation, `nat_to_int` and every renderer read a `@Nat` above `2^63 - 1` as the negative number its bits spell, so `last_digit(18446744073709551615)` returned -1, `-@Nat.0` at `2^63 + 5` returned a positive number, and a `@Nat` passed to a built-in's `@Int` parameter, `int_to_float(nat_to_int(@Nat.0))`, returned -1.0 from a module recorded as checking it.  No `@Nat` holds such a value now, and each of these is the `@Int` operation on the value it holds.
- **A `@Nat` read at an `@Int` position is neither checked nor reinterpreted** ([#1546](https://github.com/aallan/vera/issues/1546), [#1586](https://github.com/aallan/vera/issues/1586), [#1589](https://github.com/aallan/vera/issues/1589)).  A heterogeneous `@Nat`/`@Int` join built as a tuple component or produced by a `handle` returned u64.MAX as -1 with no check; a `match` arm's `@Int` binder guarded a `@Nat` that an earlier arm takes; and a `@Nat` above i64.MAX bound out of a tuple, a constructor pattern or an array trapped as a negative value.  The widening is a no-op, so none of these sites has a check to miss or to misplace.
- **Arithmetic with a literal operand runs at the signed width** ([#1543](https://github.com/aallan/vera/issues/1543), [#1591](https://github.com/aallan/vera/issues/1591), [#1593](https://github.com/aallan/vera/issues/1593)).  A non-negative literal was a `Nat` and an `if` over literals took its else branch's type, so `@Nat.0 + 1` at i64.MAX came back from an `@Int` slot as -2^63, `@Nat.0 + (if @Bool.0 then { 0 - 1 } else { 0 })` trapped as an overflow at 5, and a `@Nat` sum holding a negative literal part was read as an `@Int` unchecked.  The literal is an `Int`, the operation an `@Int` one checked against the i64 range, and each returns the true value or traps on overflow.
- **A literal above i64.MAX is E149 wherever it is written** ([#1587](https://github.com/aallan/vera/issues/1587)).  Each literal was range-checked against its own target, a `Nat` reaching `2^64 - 1`, so `0 - 18446744073709551615` proved `ensures(@Int.result < 0)` and returned 1, and a literal pattern was checked against no range, so `match @Int.0 { 9223372036854775808 -> 1, _ -> 0 }` matched -2^63.
- **`parse_int` refuses a numeral outside the `Int` range** ([#1698](https://github.com/aallan/vera/issues/1698)).  It accumulated its digits unchecked, so `parse_int("9223372036854775808")` returned `Ok(-9223372036854775808)` and a 20-digit numeral a wrapped value.  It now accumulates in the negative half of the i64 range, whose one bound serves both signs, and returns `Err("out of range")` past it, as `parse_nat` does; `-9223372036854775808` still parses.
- **A generic call's argument is checked where it narrows into a `Nat` instantiation** (an instance of [#1695](https://github.com/aallan/vera/issues/1695)).  A type argument the expected `@Nat` fixes named a clone after the arguments' own types, whose parameters carried no `@Nat` check, and a built-in checked a type-variable parameter only as a map's value: `vera run` returned -3 from a `@Nat` function for `id(0 - 3)`, `option_unwrap_or(None, -3)`, `result_unwrap_or(Err("e"), -3)` and an `array_fold` accumulator of -3, each of which `vera verify` refuses, and an argument whose sign the verifier could not decide was counted as a run-time check the module did not hold (E541 under `vera verify --reconcile`).  The argument is now checked where the verifier records it, in every user, prelude and built-in generic.
