- **An `if`, a `match` or an `Exn` handler has the type its arms share** ([#1716](https://github.com/aallan/vera/issues/1716)).  The checker recorded a join at one arm's type, keeping that arm's refinements whatever the other arms stated, so `if @Bool.0 then { @Int.0 } else { @PosInt.0 }` was a `@PosInt` and the same `if` with its branches swapped an `@Int`.  A join is now recorded at what every arm that completes states, position by position and in either order: a refinement one arm lacks, or states with another predicate, is dropped to its base (`@Int`, `Option<Int>` beside `Option<PosInt>`), and a `@Nat` beside an `@Int` is an `@Int` at every position, a non-negative literal beside a `@Nat` at the top still making a `@Nat`.  Binding such a join where the refinement is expected is the narrowing it is, obligated by its arms.  Two reports change: a generic call over such a join, `idg(if @Bool.0 then { @Int.0 } else { @PosInt.0 })` under `ensures(@Int.result > 0)`, is instantiated at `@Int`, so the `ensures` is checked at run time (`E522`) in either order, where with the `@Int` arm first it read `verified` beside an `E505` at the argument; and a `let @PosInt` bound to such a join keeps its post-fact, so an `ensures` over the binder is `verified`, where with the `@Int` arm first it was refuted (`E500`) at an input the bind's guard traps on first.
