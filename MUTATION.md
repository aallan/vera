# Mutation testing

Runbook for [#387](https://github.com/aallan/vera/issues/387) — deliberately break each line of `vera/` and confirm a test flips RED. A surviving mutant is a test gap: either a **weak test** to strengthen or an **equivalent mutant** to annotate. This is the safety net under the [#421](https://github.com/aallan/vera/issues/421) runtime decomposition and every future change.

> A passing suite is necessary, not sufficient. The #680 audit found 8 green-for-the-wrong-reason tests in one 57-test battery; #734 had to mutation-validate its own harness. Mutation testing systematises that check.

**Baseline (soundness core):** 83.3% caught, 1,773 survivors. The committed score lives in `mutation-summary.csv` and the README badge; the **per-module chart and the full survivor inventory** are attached to the [baseline comment on #387](https://github.com/aallan/vera/issues/387#issuecomment-4779424892). The nightly sweep measures all of `vera/` over a cycle of nights, and its first closed cycle's score replaces this one (§ The measure-all baseline).

## Tool: mutmut (chosen over cosmic-ray)

Evaluated both on `vera/obligations/` (Phase 0 spike, 2026-06-22):

| | mutmut 3.6 | cosmic-ray 8.4.6 |
|---|---|---|
| Throughput | **~7–8 mut/s** (coverage-guided: runs only the tests covering each mutated line) | **~0.08 mut/s** (re-runs the full test command per mutant — [#498](https://github.com/sixty-north/cosmic-ray/issues/498)) |
| Working tree | copies the project to `./mutants/`, source untouched | mutates **in place** (apply → test → revert) — leaves the tree dirty if interrupted |
| Resume after a hard kill | verdicts persist as plain JSON; `mutmut run` resumes | session SQLite; resumable |

The ~90× speed gap (coverage-guided selection) is decisive for a slow Z3/WASM suite, and the copy-based model is safer for multi-day runs. mutmut also sidesteps the stale-`.pyc` hazard of an in-place bespoke driver.

That hazard is real whenever you mutate by hand instead: when validating a test by breaking the code it targets (see TESTING.md), purge `__pycache__` before re-running — a stale `.pyc` can serve the unmutated bytecode and false-green the mutant (this bit a hand-run oracle test during the v0.0.195 work; the kill was only confirmed RED after the purge).

## Install

```bash
pip install -e ".[mutation]"   # pulls [dev] + mutmut + pytest-timeout
uv sync --locked --extra mutation --python 3.12   # the same, at uv.lock's versions, as both CI lanes install it
```

Config lives in `[tool.mutmut]` in `pyproject.toml`. (Avoid `setup.cfg` — its list values split on **newlines**, not spaces, so `a.py b.py` becomes one bogus path. TOML arrays are unambiguous.)

## Oracle: in-process unit tests only

mutmut activates a mutant **in-process** via an import trampoline. Tests that spawn a **subprocess** — `test_conformance.py`, `test_cli.py`, and `test_browser.py` all run `python -m vera.cli` / Node, which imports the **un-mutated** installed package — therefore **cannot kill mutants**. The oracle for each module is its **in-process** unit tests:

| Module | In-process oracle |
|---|---|
| `verifier.py`, `smt.py` | `test_verifier_*.py`, `test_obligations.py` |
| `checker/` | `test_checker_*.py` |
| `obligations/` | `test_obligations.py`, `test_lsp.py` |
| `codegen/`, `wasm/` | `test_codegen*.py`, `test_wasm*.py` |

Consequence for the baseline: code exercised *only* via subprocess (much of `cli.py`) will score low **because mutations are invisible there, not because its tests are weak** — mark those `# pragma: no mutate` with that reason, don't chase them as gaps.

The copy holds `vera/`, `tests/`, the config files and `also_copy`, and mutmut's stats pass runs the whole selection there with `-x`, saving its record only when it finishes, so one selected test that cannot pass in the copy stops every run with nothing kept. `also_copy` carries the repository files the selected tests read (`examples/`, `README.md`, `docs/`, `spec/`, `scripts/`, `AGENTS.md`). The copy caches bytecode: a mutated module compiles in tens of seconds (`vera/checker/calls.py` with its 3,515 mutants inlined is 24 MB and takes 47 s; `vera/wasm/calls_strings.py` with 6,547 is 67 MB and takes minutes) and loads from its `.pyc` in a fifth of a second, and under the fork server every pass and every mutant's worker is a fresh process that would otherwise compile each mutated module it reaches ([#1829](https://github.com/aallan/vera/issues/1829)); the copy is written once a run, before any import, so a stale `.pyc` cannot arise.

The oracle's boundary inside the copy is `tests/mutation_oracle.py`, a pytest plugin `[tool.mutmut]` loads, which skips two kinds of test there at the moment they do the thing. A test that starts a Python or `vera` process: each mutated module in the copy holds a copy of a mutated function for each of its mutants, so a mutated `TypeEnv._register_builtins` makes `vera/environment.py` 33.6 MB where it is 49 KB, and a process compiles every such module afresh (`vera check` of a one-line program: 2.3 s against 0.4 s) while recording nothing for the stats pass, so the test cannot be a mutant's oracle. And a test that reads a `.py` file under `source_paths` as text, or the source of one of its objects through `inspect.getsource` (#1827): what it reads in the copy is mutmut's generated file, every mutant of the mutated functions inlined, so a scan of it for a property the mutants break fails with no mutant active, which under `-x` ends the stats pass; the two verifier tests that parse `vera/verifier.py`'s text, the collision gate that runs `scripts/check_diagnostic_fields.py` over the copy's `vera/`, the two cells of `tests/test_diagnostic_codes_1490.py` that do the same, and the four tests that cost four slices of the night of 3 November 2026 their whole budget are of this kind, and no test is deselected by hand for it. A `.lark` grammar or a `.wat` runtime under `vera/` is read as before, since only `.py` files are mutated, and pytest's own reads of a traceback's source go through `tokenize.open`, which holds its own reference to the original `open`. The skipped test is out of the oracle entirely: mutmut's stats pass records the functions a test reached at the test's teardown, whatever its outcome, and runs a mutant against the tests recorded for its function, so the plugin takes a skipped test out of that record. A function that only such tests reach therefore has every mutant `no tests`, even when a test called it before starting its process or reading the file, and is reported not observable in process; the lanes list every test skipped either way, apart.

A test that fails in the copy with no mutant active, in the stats pass or the clean run, is the one that stops the pass under `-x`, and the lane drops it and runs again (§ CI: the diff lane). Under the fork server those passes run in a child whose pytest output never reaches mutmut's log, since mutmut's output catcher replaces `sys.stdout` in Python and the child's writes die with it, so the plugin appends each test that fails in those two passes to the file `MUTATION_ORACLE_FAILURES` names, and the lane reads the first when the log has no `FAILED` line ([#1829](https://github.com/aallan/vera/issues/1829)).

Both lanes run every pytest session in a process of its own: `[tool.mutmut]` sets `process_isolation = "forkserver"` (#1827). mutmut's default fork runner runs its stats pass, its test listing and its clean run as sessions of one process and forks the mutant workers from it, so state one session leaves behind breaks the next: on each of the sweep's first two nights the first session's end put the pre-session signal handlers back over wasmtime's, which installs its trap handlers once per process at the first `Engine`, and the clean pass died on its first trap (SIGILL, exit -4; #1745, #1747), and for three nights a generator parametrisation consumed by the first collection left the clean run nothing to find (#1822). The fork server runs each of those sessions in a fresh child of a parent that never imports pytest, and forks a worker per mutant from a server that only collects. Every session still carries `-p no:faulthandler` (`pytest_add_cli_args`), the first fix, now a second guard: pytest's faulthandler plugin records the handlers when a session starts and restores them when it ends, and with the plugin out nothing restores them; the price is that an engine crash leaves no Python traceback in the log. `tests/test_wasmtime_traps_across_pytest_sessions_1747.py` shows both halves of the handler mechanism on Linux, where traps are signals.

## Run a module sweep

The committed config scopes the sweep to the **soundness core** via `only_mutate` (`verifier` / `smt` / `checker` / `obligations`), while `source_paths = ["vera/"]` keeps the whole compiler in range. To sweep a different module, point `only_mutate` at it (e.g. `only_mutate = ["vera/codegen/*"]`), then:

```bash
caffeinate -dims mutmut run        # macOS: keep awake; copies to ./mutants/, runs, stores verdicts
mutmut results                     # list survivors + not-checked
mutmut show <mutant-name>          # see the exact diff for one mutant
```

`mutmut run` is **safe to interrupt** — verified against a hard `SIGKILL` mid-run: completed verdicts persist (plain JSON, no DB-corruption window) and re-running resumes, re-doing only the unfinished mutants (39s vs ~100s from scratch in the spike). A power-off costs minutes, never the whole run. Only deleting `mutants/` forces a full restart (of compute, never of correctness).

## Reading verdicts

`🎉 killed` (a test caught it — good) · `🙁 survived` (gap — triage) · `⏰ timeout` (see Z3 note) · `🔇 no tests` / `not checked` (no covering test — often a coverage gap or subprocess-only code) · `🤔 suspicious`.

## Triaging a survivor

1. `mutmut show <name>` — read the mutation.
2. Classify:
   - **Weak test** → strengthen it (a discriminating assertion or a new killing test). Same discipline as #680/#734: pick inputs where the wrong behaviour flips the assertion.
   - **Equivalent mutant** (semantically identical to the original — e.g. `a < b` vs `a <= b` where the boundary is unreachable) → `# pragma: no mutate` on the line, with a one-line rationale.
   - **Genuine coverage gap** → add a test.
3. **Re-confirm** (Z3-flakiness guardrail): re-run the specific mutant ≥2× before trusting a survivor. A mutant that makes a verification *barely* unsolvable can hit the Z3 timeout → `unknown` → Tier-3 and survive nondeterministically. If a survivor flips between runs, it's timeout-flaky, not a weak test — raise the `--timeout` / Z3 timeout rather than "fixing" a test.

## The measure-all baseline

The whole of `vera/` is measured by the nightly sweep: `.github/workflows/mutation-nightly.yml` running `scripts/mutate_sweep.py` over a random sample of the tree's mutants, a cycle a night or two. No single run holds every mutant, and no cycle tries to. At 874bc7f4 mutmut 3.8.1's visitor makes 113,127 mutants in the 2,486 functions it mutates in `vera/`, and a mutant costs from a twentieth of a second (killed by its first test) to most of an hour on a runner: a survivor runs every test that reaches its function, and a compiler's front-end functions are reached by thousands. The sweep that measured every mutant decided 300 to 1,300 a night over the nights of October 2026, so a cycle would have taken months of green nights against a tree that changes daily, and 9 of its first 18 scheduled nights were red ([#1827](https://github.com/aallan/vera/issues/1827)). The one local marathon that tried, on mutmut 3.6 and Python 3.14, deadlocked four times, 30% to 55% of the way through; the sweep has no marathon, so it does not meet that hang, and its runners use Python 3.12, as the test shards do.

**A night.** At 21:00 UTC the `setup` job finds the state the last night left: the `mutation-sweep-state` artifact of the newest completed run of this workflow on this repository's own `main`, started by the schedule or a dispatch, that holds one unexpired. A fork's run on a branch named `main`, or another workflow's run, could upload an artifact of that name, so no other run's is taken, and the state is checked field by field before it is used. Seven `sweep` jobs (`JOBS` in the script) then each plan the same night from it and run their slice:

- The inventory: every function mutmut mutates, with a hash of its text, the lines it spans: its mutants are placed by line, and the state numbers its lines from the function's first, so a change inside it (a comment or a docstring included, since either moves the lines below it) starts it afresh, and an edit above it in the file moves nothing. A function gone from the tree is dropped, and a new mutmut version starts every function afresh, since mutmut makes a function's mutants by its own rules.
- The count: each function's mutants, in all and by the line mutmut places each on (the mutated node's first line, which its covered-lines hook reads a node by; the state numbers a function's lines from its first), counted by mutmut's own visitor through the engine's `count` command (`scripts/mutate_diff.py --as-engine count`, 46 s for the whole tree on the measuring machine, about two minutes on a runner) for the functions the state holds uncounted. Each slice's record carries the counts it made, and the stitch folds them into the state.
- The sample: a line of a function is in the cycle's sample when a hash of the cycle, the function and the line falls under `SAMPLE_FRACTION` (2%), and the sample is every mutant on a sampled line, so every job of a night and every night of the cycle draw the same sample, each mutant in it with the same chance, and the next cycle draws another. At 2% of about 113,000 the sample is about 2,300 mutants, drawn in the small clusters a line holds, and the whole-tree score's 95% interval about ±2 points; a module's own interval follows its share. The sample is drawn by line because mutmut generates a kept function's mutants whole, every one into the copy: a sample of mutants drawn one by one filled a job with bins of 150 to 200 functions, which spent 30 minutes to four hours generating and compiling the copy before the first pass ran ([#1829](https://github.com/aallan/vera/issues/1829)), where a sample of lines reaches mutmut's generator through the covered-lines hook, as the diff lane's window does, and the copy holds the sample's mutants alone.
- The plan: the sample's undecided windows, a function's sampled lines decided whole, in the tree's order, in one bin a job, each bin one job's budget (4.5 h) less the passes before its first mutant (`FIXED_S`, two hours: over the fourteen slices of 29 October to 3 November 2026 with a full record, the stats pass took 45 to 130 minutes, the clean run 40 to 70 and the forced-fail run up to 25, each on one core), at an estimated cost a mutant: 25 s in the soundness core and 2.5 s elsewhere, times a factor each night measures. A bin's first window is taken whatever it costs, so a job with work open decides something.
- The run: a scratch tree of the head, narrowed to the bin's functions as the diff lane narrows a diff's, their sampled lines handed to mutmut as the window (§ CI: the diff lane), so mutmut generates the windows' mutants and no others, each function's numbered `1` to its window's count in the order of its lines. The engine counts what it generated against the window, and a listing of more or fewer mutants of a function than its window holds is a stop the night reports. mutmut's copy holds the whole tree, and the oracle is every `tests/test_*.py` file the lane's rule admits (255 of 293 today), the subprocess, Node and tooling families left out. A test that starts a Python or `vera` process, or reads the compiler's source, is no oracle in the copy (§ Oracle); one that fails there with no mutant active is dropped from the run and reported, and every night after deselects it from the start, since a drop costs a stats pass (the pass stops at the failure with nothing saved, and the rerun starts it over; four such drops cost each of four slices its whole budget on 3 November 2026), until the tree no longer holds the test's file. An exception the engine's own code raises stops the slice instead, dropping no further test, and its record and the night's report name the exception and the engine's frame (§ CI: the diff lane, The oracle).
- The `stitch` job folds the slices' counts and decided windows into the state and keeps it as the `mutation-sweep-state` artifact for 90 days.

**The cycle.** When every sampled window is decided, the cycle closes: its per-module totals, its survivors, each named by the number mutmut gives its mutant in a run over the whole function and the line it sits on (`x_g__mutmut_17@12:survived` in the state, the line counted from the function's first; `x_g__mutmut_17@L412` in `mutation-survivors.csv`, the file's line at the cycle's close, with the status beside it: the window numbers its mutants from one, and the slice maps each number back through the function's counts by line, since mutmut places a function's mutants in the order of their lines), and its sample's size are kept in the state, and that night's artifact holds `mutation-summary.csv`, `mutation.json` and `mutation-survivors.csv`. A job's budget less the fixed passes is 2.5 h of mutants, 17.5 runner hours a night; at the measured 10 to 30 s a mutant the sample is 6 to 19 runner hours, so a cycle is a night or two, and the next cycle's sample is drawn afresh. Each night's measured cost moves the plan's factor halfway to it. A function that changes during a cycle is measured again within it, so a closed cycle holds every function's code as the sweep last found it.

**The score and the badge.** A module's total is its sampled mutants an in-process test reaches with a known outcome: killed (`caught by type check` included), survived, and timeout, which counts as caught, the core baseline's convention. Its `no tests` mutants are not observable in process (§ Oracle) and are counted apart. A `segfault` or `suspicious` mutant, which a budget stop can leave behind, is taken only from a run the budget did not stop, and is counted apart too. The summary's `mutants` column is the module's population, which its `total` was drawn from, and `ci95_low` and `ci95_high` are the 95% Wilson interval of its score; the badge carries the whole tree's score with the interval's half-width (`83.1% ±1.7`). The README badge reads `mutation.json` on `main`, so a closed cycle reaches the badge by a pull request, the release pull request as a rule:

```bash
gh run download <run-id> --name mutation-sweep-state --dir state   # the night that closed the cycle
python scripts/mutate_sweep.py summary --state state               # the three files, at the repository root
```

`mutation-summary.csv` and `mutation.json` are committed; `mutation-survivors.csv`, the triage inventory, is gitignored.

**The engine and a refused state.** Both mutation lanes install `uv.lock` (`uv sync --locked --extra mutation`), so the engine is the lock's mutmut, and everything it runs with is the lock's too. A release of mutmut, pytest or any other package reaches a lane only through a lock bump, which is a reviewed pull request, and the diff lane runs both lanes' self-tests against the bumped engine on that pull request, before any night runs on it (§ CI: the diff lane). `--locked` refuses a lock that `pyproject.toml` has moved past rather than resolving afresh, and no workflow names a version of its own (`tests/test_mutate_sweep.py`'s `test_the_engine_installed_is_uv_locks`). The lanes resolved their packages afresh with pip until the night of 28 October 2026, when pytest 9.2.0, published the evening before, had dropped the private `item._nodeid` that mutmut 3.8.0's stats collector reads at every test's teardown, and the night decided nothing ([#1804](https://github.com/aallan/vera/issues/1804)). The state compares the engine's version exactly, and a new version starts every function afresh, since mutmut makes a function's mutants by its own rules, so a lock bump that moves mutmut restarts the cycle. The move to mutmut 3.8.1 restarts cycle 1 (from 2026-10-17), which stood at 12,351 of 12,922 counted mutants decided and 298 of 2,521 functions generated. The state of the sweep that decided mutants by number (schema 1, to 4 November 2026, [#1829](https://github.com/aallan/vera/issues/1829)) loads converted: the engine, the calibration and the nights (the drop memory) carry over, and every function and the cycle start afresh, since a function's identity is now its text and the sample is drawn by line; the stitch notes the conversion once and writes a plain schema 2 state. A state the script refuses (another schema, or a field out of bounds) stops every night, each one red and noted on the tracking issue, until it is replaced: delete that run's `mutation-sweep-state` artifact (`gh api -X DELETE repos/<owner>/<repo>/actions/artifacts/<id>`), and the next night carries on from the newest run before it that holds one, or from no state.

**A night that stops short.** A night that decides no mutant, a slice whose engine or lane fails, and a slice whose budget ran out before its first mutant (the four checker slices of 3 November 2026 each spent theirs in five stats passes, [#1827](https://github.com/aallan/vera/issues/1827)) end the run red, and on the schedule the `issue` job files or updates one tracking issue, labelled `mutation-sweep`, as `nightly-stress.yml` does. Survivors never do: they are the measurement. A step that fails before the sweep runs, while the runner is still there, writes a lane record in the sweep's place (`lane-failed`), reported like any other. A slice with no record is one whose runner was taken away before it could upload anything, since the `always()` steps do not run after the runner's shutdown signal: a hosted runner is lost under about 7% of the sweep's 4.5-hour jobs (8 of its first 17 seven-job nights lost one, [#1751](https://github.com/aallan/vera/issues/1751) and #1827), weather rather than a hazard. The stitch notes it, the night stays green, and the slice's work is planned again the next night; more than two slices without a record in one night is an outage, and ends the run red. The sweep job's own failure never colours the run (`continue-on-error`): the stitch does. While the engine runs, a slice prints a heartbeat line every five minutes, the elapsed time, the runner's available memory, swap and load, and the engine's last status, so the job log, which outlives a lost runner, says what the runner was doing when it went. The next night plans from the newest state, which holds what the night's other slices decided.

**On demand.** A `workflow_dispatch` run is a night of as many jobs as it is given, one by default. Nights run one at a time, and a running night is never cancelled; a night still waiting gives way to a newer one, which loses nothing, since it has planned nothing yet. Locally, `python scripts/mutate_sweep.py night --out out --budget 600` plans a one-job night from no state and runs it, and `python scripts/mutate_sweep.py stitch --slices out --out state` folds it into a state.

**A module sweep by hand.** `scripts/mutation_report.py` turns a local sweep of one module (§ Run a module sweep) into the same three files, plus the per-module chart for an issue:

```bash
python scripts/mutation_report.py --label core
```

It **fails loud** rather than emit a number it can't stand behind: an empty corpus, a result line it can't parse (mutmut format drift), a `mutmut results` status it doesn't model (`not checked` / `suspicious` / `caught by type check` — `mutmut results` lists every non-killed mutant, and these must not be folded into the derived killed count), a module missing from the `mutants/` tree, or a per-module total below its survived+timeout count is a hard error, not a skewed score. The chart (`mutation-<label>.png`) needs matplotlib, which ships in the `[mutation]` extra; the script skips the PNG with a note if it is absent. Post the headline score + per-module table as a comment on [#387](https://github.com/aallan/vera/issues/387), and drag-drop the inventory CSV and the chart into that comment (`gh` can't upload binaries; GitHub CDN-hosts them).

The core baseline it wrote, still committed until the sweep's first cycle closes: 10,620 core mutants, **83.3% caught** (7,081 killed + 1,766 timeout), 1,773 survivors — `verifier.py` dominates the survivors (875); `checker/control.py` is the weakest-covered substantive module (60.6%).

## CI: the diff lane

`.github/workflows/mutation-diff.yml` runs `scripts/mutate_diff.py` on a pull request that changes a `vera/**/*.py` file: mutmut over the lines the pull request changes, in the functions that hold them, beside the other checks. It runs, too, on a pull request that moves `uv.lock`, which names the engine both lanes install (§ The measure-all baseline, The engine and a refused state), or either lane's workflow, script or self-tests, or `tests/mutation_oracle.py`: before the script, the job runs both lanes' self-tests (`tests/test_mutate_sweep.py`, `tests/test_mutate_diff.py`) against the engine it installs, so a lock bump that breaks the engine is red on its own pull request.

**What it mutates.** The diff from the pull request's merge base, mapped to the units mutmut mutates: a top-level function, or a method of a top-level class, a nested function belonging to the one that encloses it. A unit counts as changed when its code differs from the merge base's (its `ast`, docstrings set aside) or it is new, so a docstring, a comment or a layout change alone mutates nothing. The script extracts the head commit into a scratch tree (`git archive`; the checkout is never touched) and gives every unit the diff leaves alone in a changed file `# pragma: no mutate block` on its header, so mutmut generates the changed units' mutants and no others. Inside those units it generates only the window's: the mutants whose node starts within two lines (`--context`) of a line the diff adds, or of a point where it removes lines and adds none, or on the first line of a node that spans such a line and whose mutants mutmut places on that first line though the text they change lies below it. Those nodes are a call (an argument's `None` and its removal, a `dict` keyword's rename, a string method's swap after a receiver of several lines), a `match` (a `case`'s removal), an assignment, plain, annotated or augmented, a binary or boolean operation, a comparison's operator, which starts with the line break before it, a conditional expression and a lambda (`ENCLOSING_KINDS` in the script). An edit to a diagnostic's `error_code="E302",` at `vera/checker/control.py`:430 so keeps the argument's `None` and its removal, which mutmut places on the call's first line at :419: the window holds 17 of the function's 143 mutants, where the edit's lines alone hold 5. The engine is the script itself run with `--as-engine`, which counts each unit's mutants on every line and in the window with mutmut's own visitor, then hands each narrowed file's window to mutmut's covered-lines hook (`get_covered_lines_for_file`, the filter it reads a node's start line against); a mutmut without that hook stops the run as an engine failure, and the lane checks the mutants mutmut lists against the counts. The 330 mutants of the four functions [#1760](https://github.com/aallan/vera/pull/1760) changed ran out the budget at 97 decided; 85 of them lie in the window. A file's every mutant can be far more than the diff's: `vera/verifier.py`'s are a 213 MB module that took 447 s to generate, where the 16 functions [#1715](https://github.com/aallan/vera/pull/1715) changed in it and in `vera/smt.py` took 41 s.

**The oracle.** The repository's `[tool.mutmut]` selection, plus the pull request's own changed `tests/test_*.py` files that reach the compiler in process (they import `vera`, directly or through a `tests/` helper), bar the families the selection leaves out on purpose: the subprocess, Node and tooling suites. mutmut's stats pass records which tests reach each function, and each mutant runs only those, fastest first, stopping at the first failure. A test that starts a Python or `vera` process, or reads the compiler's source, is skipped in the copy and listed (§ Oracle). Any other test that fails inside mutmut's copy with no mutant active stops the stats pass or the clean run of the covering tests; it is no oracle there, so the lane drops it, runs again (up to five drops), and lists it in the summary and the record. An exception the engine's own code raises stops the pass the same way, and no test is at fault: going outward from the traceback's innermost frame past the standard library's, the first frame is in the installed `mutmut` package (a hook of its stats pass, its trampoline). The run then stops at that attempt, red, drops no further test, and the summary and the record (`engine_error`) name the exception and that frame. A hook raising outside a test's phases is read the same way, from the traceback pytest prints as its own internal error (`INTERNALERROR>` on every line); a traceback a test printed or logged, in its report's `Captured …` sections, is no report and decides nothing. Such a section runs from its rule to pytest's next, and pytest draws its rules the terminal's width: both lanes hand the engine `COLUMNS=80`, so a rule is 79 characters or more. A `RecursionError` is the engine's only when, besides, none of its ten innermost frames outside the standard library is the copy's (`mutants/`, `tests/`), a frame Python prints once more with `[Previous line repeated N more times]` counting N more times: a recursion runs out of stack wherever the stack ends, and in the copy every call through mutmut's trampoline adds the engine's frames, so a recursion through the code under test that the suite passes can run out inside them, and stays the test's, while a function of the engine recursing on itself, even inside a test's call, fills the ten with its own frames.

**The verdict.** Red for a defect, green for an unfinished run. Exit 1 when a mutant of the diff survives, whatever else stopped the run; 2 when the run itself fails: the engine fails or counts no window, mutmut reports a mutant of a function the lane did not map to the diff, or more or fewer of a function's mutants than its window holds, which in the narrowed tree means the mapping, the narrowing or the window went wrong, or the lane itself fails before mutmut decides anything; and 0 otherwise, a run the budget stopped included. An exit 0 says in its headline what the run decided: every mutant killed or timed out, the functions no in-process test reaches, which the table names, or that the run is incomplete, when the budget ran out or a mutant was left undecided (`not checked`, `suspicious`, `segfault`, interrupted), and a `::warning::` annotation on the pull request repeats the incomplete headline. No other step of the workflow reads the exit status. A function no in-process test reaches has every mutant `no tests`; it is reported as not observable in process (§ Oracle) and does not fail the run. The job summary has a line naming the selection rule, with the changed functions, their mutants on every line and in the window, and the mutants generated, decided and surviving, then a row per changed function, the first 60 survivors' `mutmut show` diffs (a step summary over 1 MiB is dropped whole), and what the diff changes that mutmut does not mutate; the JSON record, the `mutation-diff` artifact, lists every survivor.

**The budget is the designed limit.** mutmut gets 2,400 s and the job 55 minutes. The window bounds a small edit's mutants, not a large diff's: a diff that writes new functions keeps nearly all of theirs ([#1753](https://github.com/aallan/vera/pull/1753)'s 577 mutants hold 526 in the window), a refactor across many functions keeps thousands ([#1773](https://github.com/aallan/vera/pull/1773)'s 16,031 hold 5,151), and each surviving mutant runs every test that reaches its function. Such a run ends with the partial table and, with no survivor among the mutants it decided, exit 0 and the headline `Incomplete: the budget ran out before every mutant was decided.`, which the job summary and the annotation carry: the check is green because nothing it measured failed, and the headline says the diff was not fully measured. Branch protection's required list is synced by hand and does not name the job.

**What it adds to a pull request's own mutants.** A fix pull request still runs its hand-written mutants, one per mechanism it adds, deletes or moves; the lane adds mutmut's systematic mutants over the lines it changes. A survivor is triaged as in § Triaging a survivor: a weak test to strengthen, or an equivalent mutant to mark `# pragma: no mutate` with its reason.

**Blind spots of the engine.** mutmut 3 mutates no decorated function bar one whose only decorator is `@staticmethod` or `@classmethod` (a `@contextlib.contextmanager` helper has no mutants), no method of a nested class, no module-level or class-body code, no `__new__`, `__getattribute__` or `__setattr__`, and no triple-quoted string, so a docstring is never mutated. A function evaluated at import time (called by module-level code, or a dataclass field's default) is mutated, but its mutants can never be killed: mutmut 3 forks each mutant's worker after the modules are imported, so the mutated function never runs, and every such mutant scores as a survivor ([#1740](https://github.com/aallan/vera/issues/1740)). The lane lists a changed function of the kinds mutmut does not mutate as not mutated, with the reason, and counts the changed lines outside every function.

```bash
pip install -e ".[mutation]"
python scripts/mutate_diff.py                                   # origin/main...HEAD, 2,400 s budget
python scripts/mutate_diff.py --base <sha> --budget 600 --json out.json
```
