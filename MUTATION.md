# Mutation testing

The runbook for mutation testing ([#387](https://github.com/aallan/vera/issues/387)): break each line of `vera/` on purpose and confirm a test turns red. A surviving mutant is a test gap, either a **weak test** to strengthen or an **equivalent mutant** to annotate. It is the safety net under every change to the compiler.

> A passing suite is necessary, not sufficient. A test can pass for the wrong reason, and a harness written to check tests can itself be wrong. Mutation testing checks both systematically.

**The committed score** is `mutation.json`, which the README badge reads, and `mutation-summary.csv`, per module. A release pull request writes both from the nightly sweep's last closed cycle (§ The measure-all baseline, The score and the badge); until one first does, they hold the soundness-core baseline of June 2026. The sweep measures all of `vera/` over a cycle of nights; each night's result and each cycle's survivors are comments on the standing results issue (§ The cycle's survivors). The soundness-core baseline that came before the sweep, with its **per-module chart and full survivor inventory**, is attached to the [baseline comment on #387](https://github.com/aallan/vera/issues/387#issuecomment-4779424892).

## Tool: mutmut (chosen over cosmic-ray)

Both were measured on `vera/obligations/`:

| | mutmut 3.6 | cosmic-ray 8.4.6 |
|---|---|---|
| Throughput | **about 7 to 8 mutants a second** (coverage-guided: runs only the tests covering each mutated line) | **about 0.08 mutants a second** (re-runs the full test command per mutant, [#498](https://github.com/sixty-north/cosmic-ray/issues/498)) |
| Working tree | copies the project to `./mutants/`, source untouched | mutates **in place** (apply, test, revert), and leaves the tree dirty if interrupted |
| Resume after a hard kill | verdicts persist as plain JSON; `mutmut run` resumes | session SQLite; resumable |

The 90-fold speed gap (coverage-guided selection) decides it for a slow Z3 and WASM suite, and the copy-based model is safer for runs that last days. mutmut also avoids the stale-`.pyc` hazard of an in-place driver.

That hazard is real whenever you mutate by hand instead. When validating a test by breaking the code it targets (see TESTING.md), purge `__pycache__` before re-running: a stale `.pyc` can serve the unmutated bytecode and make the mutant look killed when it is not, or survive when it is killed.

## Install

```bash
pip install -e ".[mutation]"   # pulls [dev] + mutmut + pytest-timeout
uv sync --locked --extra mutation --python 3.12   # the same, at uv.lock's versions, as both CI lanes install it
```

The config is `[tool.mutmut]` in `pyproject.toml`. Avoid `setup.cfg`: its list values split on **newlines**, not spaces, so `a.py b.py` becomes one bogus path, where a TOML array is unambiguous.

## Oracle: each module's declared in-process tests

mutmut activates a mutant **in process** through an import trampoline. Tests that start a **subprocess** (`test_conformance.py`, `test_cli.py` and `test_browser.py` all run `python -m vera.cli` or Node, which imports the **un-mutated** installed package) therefore **cannot kill mutants**. A test file is **admitted** when it is a `tests/test_*.py` module that imports `vera`, directly or through a `tests/` helper, and is not one of the families left out on purpose (`NOT_ORACLE` in `scripts/mutate_diff.py`: the subprocess, Node and tooling suites).

A module's mutants run against its **declared oracle**, the admitted files that declare it (`oracle_map` in `scripts/mutate_diff.py`, the rule `marker+name+family/1`), and no other test:

1. **Its class instruments**: every file whose `matrix` marker names the module in `decides=` (TESTING.md § Class Instruments), read from the file's syntax tree.
2. **The files named after it**: `tests/test_<stem>.py` and `tests/test_<stem>_*.py`; in a package also `tests/test_<package>_<stem>.py` and `tests/test_<package>_<stem>_*.py`; for a package's `__init__.py`, `tests/test_<package>.py`. So `tests/test_tester_distrust.py` is `vera/tester.py`'s.
3. **Its families**: `ORACLE_FAMILIES` in the same script, the one source of this table, which a self-test holds this copy to:

A family of one module names the admitted files that import it, where no instrument names it and no file is named after it. A module whose functions mutmut mutates and that nothing declares is listed in `UNDECLARED`, beside the families, with the reason; a self-test fails on a module that is neither, and on an entry that is no longer true. Its mutants are run by neither lane: the sweep decides them `undeclared`, and the diff lane names a changed function of one in its row and its headline. One module is listed: `vera/__init__.py`, whose one function reads the installed version while the package is imported.

`tests/mutation_oracle.py` enforces the declaration inside mutmut's copy. Both lanes write the map (`oracle-map.json`: every module and its declared files) and name it in `MUTATION_ORACLE_MAP`; in the stats pass, as each test ends, the plugin takes it out of mutmut's record for every function whose module's oracle does not hold its file, so a mutant runs only its module's declared tests, and the clean run of those functions does too. A map that is named and cannot be read stops the stats pass. Both lanes copy their own checkout's plugin into the scratch tree, so a run over an older head confines its oracle as today's rule says.

So a survivor means **no test the module declares kills it**, not that no test in the suite could. A test elsewhere that kills it belongs in the module's oracle: put the cell in a file the oracle holds (a class instrument naming the module, a file named after it, or a family), or, for a file whose tests kill several such mutants, add the file to a family in `ORACLE_FAMILIES`. Code exercised *only* through a subprocess (much of `cli.py`) scores low **because mutations are invisible there, not because its tests are weak**. Mark those lines `# pragma: no mutate` with that reason; do not chase them as gaps.

The repository's `[tool.mutmut]` `pytest_add_cli_args_test_selection` stays for a local `mutmut run` (§ Run a module sweep); neither lane reads it.

The copy holds `vera/`, `tests/`, the config files and `also_copy`. mutmut's stats pass runs the whole selection there with `-x` and saves its record only when it finishes, so one selected test that cannot pass in the copy stops every run with nothing kept. `also_copy` lists the repository files the selected tests read (`examples/`, `README.md`, `docs/`, `spec/`, `scripts/`, `AGENTS.md`). The copy caches bytecode, since a mutated module compiles in tens of seconds (`vera/checker/calls.py` with its 3,515 mutants inlined is 24 MB and takes 47 s; `vera/wasm/calls_strings.py` with 6,547 is 67 MB and takes minutes) and loads from its `.pyc` in a fifth of a second. Under the fork server every pass and every mutant's worker is a fresh process that would otherwise compile each mutated module it reaches. The copy is written once a run, before any import, so a stale `.pyc` cannot arise.

The oracle's boundary inside the copy is `tests/mutation_oracle.py`, a pytest plugin `[tool.mutmut]` loads. It skips two kinds of test there, at the moment they do the thing:

- A test that starts a Python or `vera` process. Each mutated module in the copy holds a copy of a mutated function for each of its mutants, so a mutated `TypeEnv._register_builtins` makes `vera/environment.py` 33.6 MB where it is 49 KB. A process compiles every such module afresh (`vera check` of a one-line program takes 2.3 s against 0.4 s) and records nothing for the stats pass, so the test cannot be a mutant's oracle.
- A test that reads a `.py` file under `source_paths` as text, or the source of one of its objects through `inspect.getsource`. What it reads in the copy is mutmut's generated file, with every mutant of the mutated functions inlined, so a scan of it for a property the mutants break fails with no mutant active, and under `-x` that ends the stats pass. The two verifier tests that parse `vera/verifier.py`'s text, the collision gate that runs `scripts/check_diagnostic_fields.py` over the copy's `vera/`, and the two cells of `tests/test_diagnostic_codes_1490.py` that do the same are of this kind. No test is deselected by hand for it.

A `.lark` grammar or a `.wat` runtime under `vera/` is read as usual, since only `.py` files are mutated, and pytest's own reads of a traceback's source go through `tokenize.open`, which holds its own reference to the original `open`. A skipped test is out of the oracle entirely. mutmut's stats pass records the functions a test reached at the test's teardown, whatever its outcome, and runs a mutant against the tests recorded for its function, so the plugin takes a skipped test out of that record. A function that only such tests reach therefore has every mutant `no tests`, even when a test called it before starting its process or reading the file, and is reported as not observable in process. The lanes list every test skipped either way, separately.

A test that fails in the copy with no mutant active, in the stats pass or the clean run, stops the pass under `-x`; the lane drops it and runs again (§ CI: the diff lane). Under the fork server those passes run in a child whose pytest output never reaches mutmut's log, because mutmut's output catcher replaces `sys.stdout` in Python and the child's writes die with it. The plugin therefore appends each test that fails in those two passes to the file `MUTATION_ORACLE_FAILURES` names, and the lane reads the first when the log has no `FAILED` line.

Both lanes run every pytest session in a process of its own: `[tool.mutmut]` sets `process_isolation = "forkserver"`. mutmut's default fork runner runs its stats pass, its test listing and its clean run as sessions of one process and forks the mutant workers from it, so state one session leaves behind breaks the next. Two such states are known: the first session's end puts the pre-session signal handlers back over wasmtime's (wasmtime installs its trap handlers once per process, at the first `Engine`), so the clean pass dies on its first trap (SIGILL, exit -4); and a generator parametrisation consumed by the first collection leaves the clean run nothing to find. The fork server runs each of those sessions in a fresh child of a parent that never imports pytest, and forks a worker per mutant from a server that only collects. Every session also carries `-p no:faulthandler` (`pytest_add_cli_args`) as a second guard: pytest's faulthandler plugin records the handlers when a session starts and restores them when it ends, and with the plugin out nothing restores them. The cost is that an engine crash leaves no Python traceback in the log. `tests/test_wasmtime_traps_across_pytest_sessions_1747.py` shows both halves of the handler mechanism on Linux, where traps are signals.

## Run a module sweep

The committed config scopes a local sweep to the **soundness core** with `only_mutate` (`verifier`, `smt`, `checker`, `obligations`), while `source_paths = ["vera/"]` keeps the whole compiler in range. To sweep a different module, point `only_mutate` at it (for example `only_mutate = ["vera/codegen/*"]`), then:

```bash
caffeinate -dims mutmut run        # macOS: keep awake; copies to ./mutants/, runs, stores verdicts
mutmut results                     # list survivors + not-checked
mutmut show <mutant-name>          # see the exact diff for one mutant
```

`mutmut run` is **safe to interrupt**, including by a hard `SIGKILL` mid-run. Completed verdicts persist (plain JSON, no window in which a database can be corrupted), and re-running resumes, redoing only the unfinished mutants (39 s against about 100 s from scratch on `vera/obligations/`). A power cut costs minutes, never the whole run. Only deleting `mutants/` forces a full restart, of compute and never of correctness.

## Reading verdicts

`🎉 killed` (a test caught it) · `🙁 survived` (a gap: triage it) · `⏰ timeout` (see the Z3 note below) · `🔇 no tests` / `not checked` (no covering test: often a coverage gap or code reached only through a subprocess) · `🤔 suspicious`.

## Triaging a survivor

1. `mutmut show <name>`: read the mutation.
2. Classify it:
   - **Weak test**: strengthen it (a discriminating assertion or a new killing test). Pick inputs where the wrong behaviour flips the assertion.
   - **Equivalent mutant** (semantically identical to the original, for example `a < b` against `a <= b` where the boundary is unreachable): put `# pragma: no mutate` on the line, with a one-line rationale.
   - **Genuine coverage gap**: add a test.
   - **Dead code**: delete it, with the evidence that no cell can tell the code present from the code absent.
3. **Re-confirm** (the Z3 flakiness guard): re-run the specific mutant at least twice before trusting a survivor. A mutant that makes a verification *barely* unsolvable can hit the Z3 timeout, become `unknown` and Tier 3, and survive nondeterministically. If a survivor flips between runs, it is timeout-flaky, not a weak test: raise the `--timeout` or the Z3 timeout rather than "fixing" a test.

## The measure-all baseline

The nightly sweep measures the whole of `vera/`: `.github/workflows/mutation-nightly.yml` runs `scripts/mutate_sweep.py` over a random sample of the tree's mutants, a cycle every night or two. No single run holds every mutant, and no cycle tries to. At 874bc7f4, mutmut 3.8.1's visitor makes 113,127 mutants in the 2,486 functions it mutates in `vera/`. A mutant costs from a twentieth of a second (killed by its first test) to most of an hour on a runner: a survivor runs every test that reaches its function, and thousands of tests reach a compiler's front-end functions. A sweep of every mutant decides 300 to 1,300 a night, so a full cycle would take months of green nights against a tree that changes daily; the sweep samples instead. Its runners use Python 3.12, as the test shards do.

**A night.** At 21:00 UTC the `setup` job finds the state the last night left: the `mutation-sweep-state` artifact of the newest completed run of this workflow on this repository's own `main`, started by the schedule or a dispatch, that holds one unexpired. A fork's run on a branch named `main`, or another workflow's run, could upload an artifact of that name, so no other run's is taken, and the state is checked field by field before it is used. Seven `sweep` jobs (`JOBS` in the script) then each plan the same night from it and run their slice:

- The inventory: every function mutmut mutates, with a hash of its text and the lines it spans. Its mutants are placed by line, and the state numbers its lines from the function's first, so a change inside it (a comment or a docstring included, since either moves the lines below it) starts it afresh, and an edit above it in the file moves nothing. A function gone from the tree is dropped, and a new mutmut version starts every function afresh, since mutmut makes a function's mutants by its own rules.
- The count: each function's mutants, in all and by the line mutmut places each on (the mutated node's first line, which its covered-lines hook reads a node by). mutmut's own visitor counts them through the engine's `count` command (`scripts/mutate_diff.py --as-engine count`, 46 s for the whole tree on a developer machine, about two minutes on a runner) for the functions the state holds uncounted. Each slice's record holds the counts it made, and the stitch folds them into the state.
- The sample: a line of a function is in the cycle's sample when a hash of the cycle, the function and the line falls under `SAMPLE_FRACTION` (2%), and the sample is every mutant on a sampled line. Every job of a night and every night of the cycle draw the same sample, each mutant in it with the same chance, and the next cycle draws another. At 2% of about 113,000 the sample is about 2,300 mutants, drawn in the small clusters a line holds, and the whole-tree score's 95% interval is about ±2 points; a module's own interval follows its share. The sample is drawn by line because mutmut generates a kept function's mutants whole, every one into the copy. A sample drawn mutant by mutant fills a job with bins of 150 to 200 functions, which take 30 minutes to four hours to generate and compile before the first pass runs. A sample of lines reaches mutmut's generator through the covered-lines hook, as the diff lane's window does, and the copy holds the sample's mutants alone.
- The plan: the sample's undecided mutants, each function's window (its sampled lines) less the mutants an earlier night decided, taken in the tree's order while their estimated cost fits the night. The night's capacity is its jobs times a job's budget (4.5 h) less the passes before its first mutant (`FIXED_S`, two hours: the stats pass takes 45 to 130 minutes, the clean run 40 to 70 and the forced-fail run up to 25, each on one core). A mutant's estimated cost is 25 s in the soundness core and 2.5 s elsewhere, times the cycle's factor (§ The cycle). The night's first function is taken whatever it costs, so a night with work open decides something. The night's modules are then cut, in the tree's order, into one run of whole modules a job (`module_bins`): a slice runs the union of its modules' declared oracles (§ Oracle), so a bin of neighbouring modules shares a small union where a bin spread over the tree would run most of the suite. Of every such cut the plan takes the one whose dearest bin costs least, which is at most a job's share and one module; every job has work while the modules outnumber the jobs. One rate per family cannot describe a bin whose undecided mutants are the dearest of their functions, since mutmut runs a bin's cheapest first, so a bin can still be over-planned; keeping each mutant as it is decided makes that harmless. A function of a module `UNDECLARED` lists is never planned: the stitch decides its sampled mutants `undeclared`, counted apart, and none is run.
- The run: a scratch tree of the head, narrowed to the bin's functions as the diff lane narrows a diff's, with their sampled lines handed to mutmut as the window (§ CI: the diff lane). mutmut generates the windows' mutants and no others, each function's numbered `1` to its window's count in the order of its lines. A function's window is fixed for the cycle (its sampled lines at its hash), so a number names one mutant on every night of the cycle, and mutmut is handed each undecided mutant by that name (`vera.verifier.xǁContractVerifierǁ_verify_fn_contracts__mutmut_41`) and no other. The names also set the clean run: mutmut runs clean the tests its stats pass recorded reaching the named functions. A glob such as `key__mutmut_*`, which mutmut matches against the functions' names, names none and leaves the clean run to the whole selection, 40 to 80 minutes of each slice on one core. Each slice runs two workers (`--max-children 2`): with four, a bin's dearest mutants, its survivors, run together at its end and take the runner into swap. The engine counts what it generated against the window, and a listing of more or fewer mutants of a function than its window holds is a stop the night reports. mutmut's copy holds the whole tree, and the selection is the union of the bin's modules' declared oracles (§ Oracle), each function's tests confined by the plugin to its own module's. Every class instrument in it runs at its sample under the cycle's seed (`cycle-<N>`), so every night of a cycle runs the same cells; at `--matrix=full` a `checker/` module's oracle is three to four times the cells. A test that starts a Python or `vera` process, or reads the compiler's source, is no oracle in the copy (§ Oracle). One that fails there with no mutant active is dropped from the run and reported, and every later night deselects it from the start until the tree no longer holds the test's file, since a drop costs a stats pass (the pass stops at the failure with nothing saved, and the rerun starts it over). An exception the engine's own code raises stops the slice instead, dropping no further test, and its record and the night's report name the exception and the engine's frame (§ CI: the diff lane, The oracle).
- The `stitch` job folds the slices' counts and decided mutants into the state, a mutant at a time, and keeps it as the `mutation-sweep-state` artifact for 90 days. A window partly decided keeps its decided mutants (`partial`, by window number) and becomes a decided window when its last mutant is decided; mutmut runs a bin's mutants in ascending order of estimated cost across the whole bin, so a rule that counted only whole windows would decide the same cheap mutants night after night and record few of them. A slice's record holds each decided mutant's duration as its own run measured it: the oracle plugin writes the run's start when its session starts and its end when the session ends, and the duration is the end less the start (mutmut's fork server reports every duration as zero, and the calibration leaves a zero out). A run with no end, which the cap's exit or a kill ended, has no measured duration and stays out of the calibration. The record also holds mutmut's estimate of each mutant, the times the engine's phases started and its first mutant was decided, the engine's last count, and the runner's lowest available memory and highest swap; a survivor's entry holds its line, the hash of that line's text and the test files it ran against.

**The cycle.** When every sampled mutant is decided, the cycle closes, whatever else the night did (only a validated record merges, so a lost or failed slice cannot close it wrongly). The state keeps its per-module totals, its sample's size and its survivors. Each survivor is named by the number mutmut gives its mutant in a run over the whole function and the line it sits on: `x_g__mutmut_17@12:survived` in the state, the line counted from the function's first, and `x_g__mutmut_17@L412` in `mutation-survivors.csv`, the file's line at the cycle's close, with the status beside it. The window numbers its mutants from one, and the slice maps each number back through the function's counts by line, since mutmut places a function's mutants in the order of their lines. That night's artifact holds `mutation-summary.csv`, `mutation.json` and `mutation-survivors.csv`. A job's budget less the fixed passes is 2.5 h of mutants, 17.5 runner hours a night; at 10 to 30 s a mutant the sample is 6 to 19 runner hours, so a cycle takes a night or two, and the next cycle's sample is drawn afresh. The plan's factor is the cycle's own: its decided mutants' summed recorded duration over their summed estimate (`calibration_cycle` in the state), so a cycle's last nights, which decide each window's dearest mutants, no longer carry into the next cycle's first; a new cycle starts at the closed one's whole ratio. A function that changes during a cycle is measured again within it, so a closed cycle holds every function's code as the sweep last found it.

**The oracle in the state.** The state keeps the rule its windows were decided under (`oracle_rule`, `marker+name+family/1`) and each module's oracle digest (`oracles`: a hash of the rule, the module's declared test files and the seed rule `cycle-<N>/sample`). The slices and the stitch read the oracle at the night's head and take the state alike: a state under another rule, or from before the rule (each mutant run against the tests that cover it), leaves its open cycle and starts the next, every window undecided and the factor at 1.0, since every mutant's cost changes; under the same rule, a module whose digest changed has its windows reopened, since they were decided against other tests.

**The score and the badge.** A module's total is its sampled mutants an in-process test reaches with a known outcome: killed (`caught by type check` included), survived, and timeout, which counts as caught, the core baseline's convention. Its `no tests` mutants are not observable in process (§ Oracle) and are counted separately, as are its `undeclared` ones, which no test declares and no slice ran. A survivor means that no test the module declares kills it, not that no test in the suite could (§ Oracle). A `segfault` or `suspicious` mutant, which a budget stop can leave behind, is taken only from a run the budget did not stop or one whose engine recorded it before the stop was sent, and is counted separately too, as are `memory` and `lost` (§ A night that stops short, The memory bound). A survivor of a function evaluated at import is reported outside the total too (§ The cycle's survivors).

A `slow` mutant is one whose run reached the cap of 2,400 s, which the oracle plugin enforces with a timer in mutmut's worker (`MUTATION_ORACLE_CAP_S`): it names the mutant in the file `MUTATION_ORACLE_SLOW` names and ends the run with exit 2, which mutmut reads as interrupted. The slice records a mutant the file names as `slow` where mutmut left it undecided (interrupted, or not checked). A verdict mutmut completed stands even when the file names the mutant, since the timer cannot be withdrawn once its wait has returned, and a mutant mutmut marks interrupted that the file does not name stays undecided. A slow mutant is decided for the cycle, counted separately, never caught and never a survivor, and listed in `mutation-survivors.csv` with its status; that its tests take that long is itself a finding. mutmut's own bound, half its CPU limit, `(est + 1) × 15` s, still ends a mutant whose covering tests take under 159 s clean first, as a caught timeout.

The summary's `mutants` column is the module's population, which its `total` was drawn from, and `ci95_low` and `ci95_high` are the 95% Wilson interval of its score; the badge shows the whole tree's score with the interval's half-width (`83.1% ±1.7`). The README badge reads `mutation.json` on `main`, so a closed cycle reaches the badge through a pull request, usually the release pull request:

```bash
gh run download <run-id> --name mutation-sweep-state --dir state   # the night that closed the cycle
python scripts/mutate_sweep.py summary --state state               # the three files, at the repository root
```

`mutation-summary.csv` and `mutation.json` are committed; `mutation-survivors.csv`, the triage inventory, is gitignored.

**The engine and a refused state.** Both mutation lanes install `uv.lock` (`uv sync --locked --extra mutation`), so the engine is the lock's mutmut, and everything it runs with is the lock's too. A release of mutmut, pytest or any other package reaches a lane only through a lock bump, which is a reviewed pull request, and the diff lane runs both lanes' self-tests against the bumped engine on that pull request, before any night runs on it (§ CI: the diff lane). `--locked` refuses a lock that `pyproject.toml` has moved past rather than resolving afresh, and no workflow names a version of its own (`tests/test_mutate_sweep.py`'s `test_the_engine_installed_is_uv_locks`). The state compares the engine's version exactly, and a new version starts every function afresh, since mutmut makes a function's mutants by its own rules, so a lock bump that moves mutmut restarts the cycle. A state written under an older schema loads converted to the current one (schema 3): a schema 2 state keeps its cycle, with no window partly decided, and a schema 1 state (mutants decided by number) keeps its engine, its calibration and its nights, while every function and the cycle start afresh, since a function's identity is now its text and the sample is drawn by line. The stitch notes the conversion once and writes a plain schema 3 state. A state the script refuses (another schema, or a field out of bounds) stops every night, each one red and noted on the tracking issue, until it is replaced: delete that run's `mutation-sweep-state` artifact (`gh api -X DELETE repos/<owner>/<repo>/actions/artifacts/<id>`), and the next night carries on from the newest run before it that holds one, or from no state.

**A night that stops short.** A budget stop is a normal stop: the slice keeps each mutant it decided, the night notes the stop, and the next night plans the rest. The run ends red on any of these: a slice whose engine or lane fails, or whose listing maps a mutant to no planned window; records that disagree (another head, state, night or engine); more than two slices with no record; a plan with nothing in it while the cycle is open; a second night in a row that decides no mutant. On the schedule the `issue` job then files or updates one tracking issue, labelled `mutation-sweep` and found by its title, as `nightly-stress.yml` does; the standing results issue carries the same label and never takes a failure report. One night that decides nothing is not red: a bin of slow mutants or a lost runner can cause it, and the next night plans the same work. A night whose planned slices all sent no record decided nothing too, so losing the one working slice night after night is red on the second. Only nights written under schema 3 count toward the two, since a night line schema 2 wrote counted whole windows alone, and its `moved` of 0 says nothing of what its engines decided. Survivors never make a night red: they are the measurement. A step that fails before the sweep runs, while the runner is still there, writes a lane record in the sweep's place (`lane-failed`), reported like any other.

A slice with no final record is one whose runner was taken away before it could upload it, since the `always()` steps do not run after the runner's shutdown signal. A hosted runner is lost under about 7% of the sweep's 4.5-hour jobs, which is weather rather than a hazard. The stitch notes it, the night stays green, and the slice's work is planned again the next night; more than two slices without a record in one night is an outage, and ends the run red. The sweep job's own failure never colours the run (`continue-on-error`); the stitch does. The next night plans from the newest state, which holds what the night's other slices decided.

**The legs.** A lost runner takes its job's log with it, so the slice runs in the background across the job's steps (`mutate_sweep.py start`) and rewrites its partial record at every heartbeat: the plan, each mutant decided so far with its status and duration, the mutants in flight, the phase times, and a heartbeat series of the runner's available memory, swap, load and free disk and the bound's processes, memory and kill count. Ten leg steps (`mutate_sweep.py leg`), the plan's and then one every 30 minutes, each print the slice's output into the job log as it grows and upload the partial record as `mutation-sweep-slice-<n>-leg-<k>`, kept three days. Every leg step and leg upload continues on error (`continue-on-error`), so a leg that fails (a full disk, an upload refused) never ends the slice, and each upload runs on a cancelled run too (`if: always()`). The last step (`finish`) runs whatever the legs did and waits for the slice, and its final record is uploaded as `mutation-sweep-slice-<n>` whatever happened (`if: always()`).

A partial record never holds less than an earlier one. When a `mutmut results` listing fails, times out or raises (mutmut writes a mutant's meta file with a plain write, so a listing can meet one mid-write), the record keeps the results last read whole and says when the listing failed, and a final record whose own listing failed keeps them too, under the engine's stop. The stitch takes a slice's final record, and for a slice with none its legs together. A decision is final, so a mutant any valid leg decided is decided; two legs that decide one mutant differently are a problem and leave it undecided; the mutants in flight and the heartbeat series are the last leg's; and the slice counts as lost. A slice whose driver ended with no record, or raised after its engine ran, keeps what its last partial record decided under a lane stop. A slice of a cancelled run ends with no final record too: the stitch is told the sweep job's result and charges no loss on a cancelled run. A job that reached its own timeout cannot be told from a lost runner, so the sweep job's timeout (330 minutes) holds the budget, the engine's grace, its last listing and the legs, which wait no longer than the budget from the slice's start.

**The memory bound.** The slice runs in a transient systemd scope (`scope_command`, set up with the hosted runner's own `sudo`) whose memory is the runner's less 2.5 GiB, with no swap and `OOMPolicy=continue`, as the runner's user with its environment. The oracle plugin writes 1000 to each mutant's run's `oom_score_adj` and the engine runs at 500, so when a run outgrows the bound the kernel prefers to end that run, and the runner, outside the scope, lives. The adjustment is a preference, not a guarantee. The kernel also weighs the memory each process holds, so it ends the engine instead when the engine holds more than half the bound beyond what the run holds, and the slice's record then shows an engine stop with the bound's `oom_kill` count risen. A bound that is not in place stops the slice as a lane failure: the night never runs unbounded.

mutmut reports a worker ended by signal 9 as `segfault`, as it does one that RLIMIT_CPU's hard limit ends, so the slice decides `memory` only on evidence. The plugin records each run's start and process, and a run whose process disappeared while the bound's `oom_kill` count rose, with mutmut's `-9`, is `memory`, when the rise covers every such run. The attribution is by count within a poll interval (10 s): a rise is matched with the runs whose process disappeared at that look or the one before. It cannot mistake a run that ended with a verdict, a run whose process is still there, or a `-9` with no rise (RLIMIT_CPU's hard limit). It could mistake a mutant's `-9` for `memory` when, in the same interval, the kernel ended some other process of the scope that is not a mutant's run; mutmut 3.8.1 sends a worker SIGKILL only after the budget's stop, where `CUT_SHORT` waits anyway.

On a run not cancelled, a slice whose end is a lost runner or an engine that stopped, with neither the engine finishing nor the budget stopping it, charges a loss to each mutant in flight at the last record it uploaded (a lost runner's last leg, written up to a leg before the loss; an engine stop's final record) whose run had lasted at least a heartbeat interval (five minutes) when the record was written. What happened after that record is not known, so a run that had just started draws no loss, and a mutant that takes the runner within minutes of its start is named instead by the rule for a slice lost two nights on one plan. A record written once the budget's stop was sent charges none (the slice rewrites its partial record as the stop is sent, and reads that the stop was sent where it writes each record), even where the final listing then fails and the slice reads as stopped by the engine: the budget cut those runs short. The slice's report names a loss by the same rule. At two losses a mutant is `lost`. Both `memory` and `lost` are decided, counted separately and listed, never caught and never survived. A slice lost two nights running on the same plan, with no mutant of it decided either night, ends the run red.

A `segfault` or `suspicious` mutant the engine recorded before a budget stop was sent is kept; one that appears after it waits, in a partial record listed during the stop's grace as in the final one. What the engine recorded before the stop is what its meta files held as the stop was sent and what any listing that ended before it showed. A listing is placed by its child's exit time against the time the stop was sent, not by which thread read it first, so a listing that ended just before the stop but was read after it keeps what it showed. The diff lane runs without the bound.

**On demand.** A `workflow_dispatch` run is a night of as many jobs as it is given, one by default. Nights run one at a time on each ref, and a running night is never cancelled; a night still waiting gives way to a newer one, which loses nothing, since it has planned nothing yet. A dispatch on a branch is a group of its own, so it neither waits behind nor displaces a night on `main`.

**A redraw.** A dispatch with `redraw` set to a closed cycle's number decides that cycle's sample again under the declared oracle, to compare the two oracles: over the functions whose code is unchanged since the cycle (their hash in the state equals the head's), every window undecided, at factor 1.0. Its state is a branch's: it closes no cycle, and no night on `main` reads it. `state_run` names the run whose state the night carries on from in place of the lookup: one of this workflow's completed runs on this repository, started by the schedule or a dispatch, on any branch, holding an unexpired state, so a redraw's second night carries on from its first. A run on `main` takes neither input: the setup job refuses it before any state is downloaded, and the lookup takes only runs on `main`, so no branch's state and no redraw's enters the chain the committed score is read from. The stitch notes which run's state the night read, and its branch. Each slice of a redraw keeps back 30 minutes of its budget (`PROBE_RESERVE_S`) for its **flips**, the mutants the cycle killed that the declared oracle leaves (survived, or reached by no declared test): for each, pytest runs in mutmut's generated tree with the flip active, over the admitted files its module's oracle does not hold (the bin's other modules' first), until the first failure, which the oracle plugin names (`MUTATION_ORACLE_KILLERS`), at most 10 minutes a flip. No mutmut run, so no stats pass. The stitch keeps every compared mutant's outcome in the state's `redraw`, across nights, and writes `differential.json` beside the state, with a table in its summary: per module, the compared mutants decided, killed then and now, flips with each one's killer by file, and survived then and killed now. A mutant the cycle decided `no tests` is not listed in its record, so it reads as killed then; a flip of one names no killer. A killer file behind several flips of a module joins its family in `ORACLE_FAMILIES`; a lone one is a cell its module's oracle lacks. Locally, `python scripts/mutate_sweep.py night --out out --budget 600` plans a one-job night from no state and runs it, and `python scripts/mutate_sweep.py stitch --slices out --out state` folds it into a state.

**A module sweep by hand.** `scripts/mutation_report.py` turns a local sweep of one module (§ Run a module sweep) into the same three files, plus the per-module chart for an issue:

```bash
python scripts/mutation_report.py --label core
```

It **fails loud** rather than emit a number it cannot stand behind. Each of these is a hard error, not a skewed score: an empty corpus; a result line it cannot parse (mutmut format drift); a `mutmut results` status it does not model (`not checked`, `suspicious`, `caught by type check`: `mutmut results` lists every mutant not killed, and these must not be folded into the derived killed count); a module missing from the `mutants/` tree; a per-module total below its survived plus timeout count. The chart (`mutation-<label>.png`) needs matplotlib, which ships in the `[mutation]` extra; the script skips the PNG with a note if it is absent. Post the headline score and per-module table as a comment on [#387](https://github.com/aallan/vera/issues/387), and drag the inventory CSV and the chart into that comment (`gh` cannot upload binaries; GitHub hosts them on its CDN).

The soundness-core baseline it wrote, before the sweep, is on [#387](https://github.com/aallan/vera/issues/387#issuecomment-4779424892) with its per-module table and survivor inventory; the sweep's closed cycles measure the whole tree in its place.

## The cycle's survivors

Each night's result and each cycle's survivors go to one issue that stays open: `Mutation sweep results (standing)`, labelled `testing` and `mutation-sweep`, which the workflow's `results` job finds by its title and creates, with a body saying how to read it, when it is absent. No night closes it.

**A night's comment.** Every scheduled night, red or green, posts one comment there: the commit and the run, the mutants decided that night by verdict (killed, survived, timeout, slow, memory, lost, evaluated at import, no tests, undeclared), the cycle's progress, the slices (with work, stopped by the budget, lost, and the first mutant's minutes), and the night's new survivors counted by module, in at most 25 lines. A night that decided nothing says so in three. A red night's comment says so in one line and points at the run's stitch summary; a scheduled night's also names the tracking issue, whose report is unchanged (§ A night that stops short). A night whose stitch rendered no comment (it failed, or never ran because the setup failed) posts two lines instead, marked apart from a night's comment, that link the run. The stitch writes what the state took that night beside the state (`night-report.json`), `mutate_sweep.py comment` renders the comments from it in the stitch job, and the `results` job, which can write issues and nothing else and checks out no code, posts each with `gh issue comment --body-file`. Each comment's first line is a marker naming its run, or its cycle, the date of the cycle's first night and the part (`cycle=N from=YYYY-MM-DD gen=G part=K`, where `G` is the id of the run that created the state, its `generation`, absent from a state created before the field, so a state reset that counts from 1 again cannot collide with an older cycle, even one begun on the same day), and a comment whose marker the issue already holds is not posted again, so a rerun posts nothing twice. Only a run on `main` posts a cycle's close comment: a scheduled night, or a dispatch on `main` with `post`, and only when its stitch job uploaded the state that keeps the parts (the job's `state` output), since a later night that starts from an older state would render them again under the same markers. A dispatched run on any other ref renders the cycle's parts into its `mutation-sweep-comment` artifact, posts none of them whatever `post` says, and says so in its stitch summary; its night's comment, with `post`, is posted, and names the ref. The proof night of the pull request that brings the loop runs on its branch, so it creates the standing issue and posts one dispatched night's comment; cycle 2's close comment is posted by the first scheduled night on `main` after the merge. The stitch job's `comments` output, the comments' artifact id, tells the `results` job whether there is anything to download, so comments that exist and fail to download fail the job, which can be rerun. A dispatched run posts only when its `post` input is set, and its comment's first line says it was dispatched.

**A cycle's close comment.** The night that closes a cycle also posts the cycle's comment: its score by module with the 95% interval, the change against the cycle before (the closed record keeps that cycle's counts per module, `previous`; the first cycle to close says there is none), the command that writes the committed score from the run's state for that cycle (`summary --cycle N`, which reads the kept cycle's record; without `--cycle`, the last closed cycle's), the cycle before's score read by the rule at its own head, and the cycle's survivors as a task list, grouped by module in collapsed sections, each line naming the file, the line, the function, the mutant's number and the mutation itself: the code mutmut changes and what it changes it to, read from mutmut's own visitor at the cycle's head (`mutate_diff.py`'s engine `show-mutations` command, with `uv.lock`'s engine installed on the night that renders the comment). Where the engine cannot show it, or places it on another line than the state's, the line names its text instead. A comment that would pass 60,000 characters goes on in a second, by module, and a module's tasks, or the slow and at-import lists after them, longer than a comment are cut between two entries, the heading repeated. The close itself keeps the cycle's record in the state (`comments`), with those of the two cycles closed before it, newest first: its counts by module, each listed mutant (survived, timeout, slow, memory, lost) by module, function, number, line and the engine's status, and the engine's version, so a cycle whose comment was not rendered (the render failed or ran out of time) is rendered from its record on a later night, even after the next cycle closes. A kept cycle is named by its number and its first night together; a save keeps only the cycles before the newest in both, so an earlier sequence's (after a state reset) is dropped. The comment is rendered once and its parts kept beside the record: at most 3 records of 10,000 listed mutants of 300 characters (9 MB) and 3 cycles of 10 parts of 65,536 characters (2 MB), where cycle 2's record was 43 KB and its comment two parts and 82 KB. A render that fails those bounds is neither kept nor posted, and the next night renders it again. Every later night writes the kept parts and posts each whose marker the issue lacks, so a part missed on one night reaches the issue on a later one as it was cut. The engine shows the mutations only when its version is the one that ran the cycle, and its calls share 300 s of the render step's 600 s; otherwise each task names its line's text.

**A survivor ends as one of three things,** each in a pull request that ticks its line:

- a killing cell in a file the module's declared oracle holds (§ Oracle: a class instrument whose `matrix` marker names the module, a file named after it, or a family), so the next cycle's oracle holds it;
- `# pragma: no mutate` on the line, with `equivalent: <reason>`, for a mutant no input can tell from the code;
- a deletion, with the evidence that no cell can tell the code present from the code absent.

A slow mutant is listed apart: that its tests take that long is itself a finding.

**Evaluated at import, not observable in process.** mutmut forks a mutant's worker after the modules are imported, so a function that runs only while a module is imported does not run under its mutant, and its mutants survive ([#1740](https://github.com/aallan/vera/issues/1740)). The sweep finds such functions by a rule over the sources, `at_import_units`, read at its conservative closure: a function is one only if it has a mention and every mention of it in `vera/` and `tests/` is a direct call, by its plain name in its own module, in code run while that module is imported (a module or class body, a default, an annotation in a module that does not postpone annotations, the body of another such function, the import branch of a `__main__` guard). Any other mention makes it observable: an import of its name into another module or a test (a re-export, aliased or not, or `*`), its name as a string (`__all__`, `getattr`, `monkeypatch`), an attribute of that name, a name stored, passed or returned, a decorator, a call in the body of a method, a nested function or a lambda, in a generator expression past its leftmost iterable, in an annotation under `from __future__ import annotations`, or in the script branch of a `__main__` guard. A mention is matched by the bare name, so it makes every function of that name observable. Where in doubt, a mention is one that runs later, which keeps the survivor on the task list. A generator or coroutine function, or a decorated one, runs its body later, as does a `type` alias's value. The rule decides nothing the engine runs: every mutant is planned, run and kept as the engine decides it. It is applied where a result is reported (the night's comment, the cycle's comment and `summary`): a mutant the engine recorded as survived, of a function the rule selects at that cycle's head, is counted and listed as evaluated at import, outside the survivor tasks and the score's total, and a mutant the engine killed, timed out or found no tests for is reported as the engine decided it. So a misreading can at worst move a real survivor from the task list to the at-import line; it can never hide a killed or killable mutant (a module first imported inside a test body, for one, runs its mutants after the fork, and they are reported killed). The rule selects 26 functions in the tree.

## CI: the diff lane

`.github/workflows/mutation-diff.yml` runs `scripts/mutate_diff.py` on a pull request that changes a `vera/**/*.py` file: mutmut over the lines the pull request changes, in the functions that hold them, beside the other checks. It also runs on a pull request that moves `uv.lock`, which names the engine both lanes install (§ The measure-all baseline, The engine and a refused state), or either lane's workflow, script or self-tests, `scripts/mutation_report.py` or `tests/mutation_oracle.py`. Before the script, the job runs both lanes' self-tests (`tests/test_mutate_sweep.py`, `tests/test_mutate_diff.py`) against the engine it installs, so a lock bump that breaks the engine is red on its own pull request.

**What it mutates.** The diff from the pull request's merge base, mapped to the units mutmut mutates: a top-level function, or a method of a top-level class, with a nested function belonging to the one that encloses it. A unit counts as changed when its code differs from the merge base's (its `ast`, docstrings set aside) or it is new, so a docstring, a comment or a layout change alone mutates nothing. The script extracts the head commit into a scratch tree (`git archive`; the checkout is never touched) and gives every unit the diff leaves alone in a changed file `# pragma: no mutate block` on its header, so mutmut generates the changed units' mutants and no others.

Inside those units it generates only the window's mutants: those whose node starts within two lines (`--context`) of a line the diff adds, or of a point where it removes lines and adds none, or on the first line of a node that spans such a line and whose mutants mutmut places on that first line though the text they change lies below it. Those nodes are a call (an argument's `None` and its removal, a `dict` keyword's rename, a string method's swap after a receiver of several lines), a `match` (a `case`'s removal), an assignment (plain, annotated or augmented), a binary or boolean operation, a comparison's operator, which starts with the line break before it, a conditional expression and a lambda (`ENCLOSING_KINDS` in the script). For example, an edit to a diagnostic's `error_code="E302",` at `vera/checker/control.py`:430 keeps the argument's `None` and its removal, which mutmut places on the call's first line at :419: the window holds 17 of the function's 143 mutants, where the edit's lines alone hold 5.

The engine is the script itself run with `--as-engine`. It counts each unit's mutants on every line and in the window with mutmut's own visitor, then hands each narrowed file's window to mutmut's covered-lines hook (`get_covered_lines_for_file`, the filter it reads a node's start line against). A mutmut without that hook stops the run as an engine failure, and the lane checks the mutants mutmut lists against the counts. The window matters: the 330 mutants of the four functions [#1760](https://github.com/aallan/vera/pull/1760) changed ran out the budget at 97 decided, and 85 of them lie in the window. A file's every mutant can be far more than the diff's: `vera/verifier.py`'s are a 213 MB module that took 447 s to generate, where the 16 functions [#1715](https://github.com/aallan/vera/pull/1715) changed in it and in `vera/smt.py` took 41 s.

**The oracle.** Each changed module's declared oracle (§ Oracle), with the pull request's own changed `tests/test_*.py` files that reach the compiler in process (they import `vera`, directly or through a `tests/` helper), bar the subprocess, Node and tooling suites, added to each changed module's. The selection is their union, and the plugin confines each function's tests to its own module's, so a function's mutants run against its module's declared files and the pull request's, never against another changed module's. Every class instrument runs at its sample in the engine's run, under a seed fixed for the run (`diff-<head>`). A lane names its seed to the engine in the variable `VERA_MATRIX_SEED`, which the sample reads when no `--matrix-seed` is given, and never as an argument: mutmut hands its pytest arguments to every run it starts, and a run whose plugins do not define the option refuses it. Run in full under mutmut's stats tracer, the instruments of a six-module checker change are 25,860 cells against 7,302 at the sample, and the stats pass of [#1907](https://github.com/aallan/vera/pull/1907)'s replay (run 45406471525) took the whole budget with no mutant decided. The cells the sample leaves out look at the survivors instead: the engine gets the budget less 600 s (`FULL_PROBE_RESERVE_S`), and in what is left each survivor on the diff's own lines is run again, the mutant active, with pytest in mutmut's generated tree over its module's class instruments at `--matrix=full`, stopping at the first failure, at most 300 s a survivor (`full_cell_probe`). A failing test kills it only if that test, run alone in the same tree with no mutant active, passes (once a test, at most 120 s): then the survivor is recorded killed, with that test's id, and does not fail the check; a test that fails on its own leaves the survivor, marked "its only failing test fails with no mutant active". A look that finds no failing test, does not finish in its bound, or cannot run (no instrument names the module) leaves it a survivor, its reason beside it, and it fails the check. When the 600 s run out before a survivor's turn, it stays a survivor marked "not looked at", and the check is red: answer it as any survivor, or run the lane again. The summary's budget line gives the split in seconds. A mutant only a sampled-out cell kills is so never a survivor ([#1926](https://github.com/aallan/vera/pull/1926)'s eight in `_emit_written_store_guard`), at a cost that grows with the survivors, not with the instruments. A changed function of a module listed in `UNDECLARED` (or that nothing declares) is not mutated; its row says so, with the reason, and so does the headline. mutmut's stats pass records which tests reach each function, and each mutant runs only those, fastest first, stopping at the first failure. A test that starts a Python or `vera` process, or reads the compiler's source, is skipped in the copy and listed (§ Oracle). Any other test that fails inside mutmut's copy with no mutant active stops the stats pass or the clean run of the covering tests. It is no oracle there, so the lane drops it, runs again (up to five drops in all), and lists it in the summary and the record.

**Two passes.** mutmut runs a run's mutants in ascending order of estimated cost across every function it is handed, so one run over all of a diff's mutants leaves the most widely covered function, whose every mutant is the dearest, undecided whenever the budget runs out ([#1917](https://github.com/aallan/vera/pull/1917)'s runs left `_Builder.walk`'s 160 all unchecked). The first pass hands mutmut each changed function's first window mutant by name; mutmut reads the clean run's tests off the names it is handed, so the clean run is the changed functions' covering tests (a glob, matched against the functions' names, adds none, and a run of globs alone runs the whole selection clean). The second pass hands it, by name, every mutant of the diff the first left undecided, in what is left of the budget, with the same configuration, so the stats the first recorded stand. The summary has a row per pass: the mutants it named, when each of the engine's phases started (stats, listing, clean run, forced fail, mutants, the first mutant decided), in seconds from the lane's start, its run's length and what it decided; the record's `passes` holds the same.

An exception the engine's own code raises stops the pass the same way, and no test is at fault. Going outward from the traceback's innermost frame past the standard library's, the first frame is in the installed `mutmut` package (a hook of its stats pass, its trampoline). The run then stops at that attempt, red, drops no further test, and the summary and the record (`engine_error`) name the exception and that frame. A hook raising outside a test's phases is read the same way, from the traceback pytest prints as its own internal error (`INTERNALERROR>` on every line). A traceback a test printed or logged, in its report's `Captured …` sections, is no report and decides nothing. Such a section runs from its rule to pytest's next, and pytest draws its rules the terminal's width: both lanes hand the engine `COLUMNS=80`, so a rule is 79 characters or more. A `RecursionError` is the engine's only when, in addition, none of its ten innermost frames outside the standard library is the copy's (`mutants/`, `tests/`), a frame Python prints once more with `[Previous line repeated N more times]` counting N more times. A recursion runs out of stack wherever the stack ends, and in the copy every call through mutmut's trampoline adds the engine's frames, so a recursion through the code under test that the suite passes can run out inside them, and stays the test's; a function of the engine recursing on itself, even inside a test's call, fills the ten with its own frames.

**The verdict.** Red for a defect or a diff not measured, green for a run that measured every changed function. A pull request is gated on its own lines: a survivor whose mutation is on a line the diff adds or modifies (its node starts there, or it removes or replaces a child that starts there, the rule mutmut reads an ignored line by) fails the check, and one on an unchanged line the two-line window pulled in does not. Such a neighbour survivor is listed apart, with its diff, in the summary and in the JSON record (`neighbour_survivors`), the headline counts it separately, and the pull request does nothing about it: the standing sweep issue, [#1888](https://github.com/aallan/vera/issues/1888), owns it. A hunk that removes whole statements leaves no line of the pull request's own, so the mutants around it are measured and listed and gate nothing; a mutation whose node spans the point where lines were removed (a condition, call or literal that lost a line) is the pull request's own, since the diff edited that node. The script exits 1 when a mutant on the diff's own lines survives under its module's declared oracle, whatever else stopped the run. It exits 2 when the run itself fails: the engine fails or counts no window; mutmut reports a mutant of a function the lane did not map to the diff, or more or fewer of a function's mutants than its window holds, which in the narrowed tree means the mapping, the narrowing or the window went wrong; or the lane itself fails before mutmut decides anything. It exits 3 when the diff is not measured: a changed function with mutants in its window had none decided, because the budget ran out first, the engine never reached it, every one it ran ended undecided (`not checked`, `suspicious`, `segfault`, interrupted), or no test of its module's declared oracle reaches it (every mutant `no tests`: the row names the module). The headline says `Not measured: N function(s) had no mutant decided`, and each such row says `not decided` or `not measured`. It exits 0 otherwise. An exit 0 says in its headline what the run decided: every mutant killed or timed out, the functions no in-process test reaches (which the table names), or that the run is incomplete, when every changed function had a mutant decided and the budget ran out, or a mutant was left undecided, before all were. A `::warning::` annotation on the pull request repeats the incomplete headline. No other step of the workflow reads the exit status. The job summary has a line naming the selection rule, with the changed functions, their mutants on every line and in the window, and the mutants generated, decided and surviving; the oracle; the passes; then a row per changed function, the first 60 survivors' `mutmut show` diffs (a step summary over 1 MiB is dropped whole), and what the diff changes that mutmut does not mutate. The JSON record, the `mutation-diff` artifact, holds every survivor with its diff, asked of the engine within 300 s in all; a survivor past that is named with `(not shown: the show budget ran out)`.

**What a red check asks of the pull request.** Exit 1: answer each survivor on the diff's own lines in the tree with a cell that kills it in a file its module's oracle holds (a class instrument whose marker names the module, a file named after it, or a family), `# pragma: no mutate` on the node's own line with a measured reason, or a deletion (§ Triaging a survivor). A survivor that a test outside the oracle kills is still a survivor here: the cell belongs in the oracle, or the test's file in `ORACLE_FAMILIES`. Exit 2: the lane failed; the summary's last lines say where. Exit 3: the run says nothing of the functions it names; run it again (a new push), split the change so each part's functions fit the budget, or record in the pull request a hand battery over those functions' window mutants.

**The list.** Before the self-tests and the lane, a step runs `mutate_diff.py --list`: the window's mutants of each changed function, each with its line and the code mutmut changes and what it changes it to, from mutmut's own visitor over the narrowed files and no test run, kept as the `mutation-diff-list` artifact. A first push can be answered from it while the lane still runs. The step informs and decides nothing, so its failure does not fail the job. `--list` runs mutmut's generator alone, no test and no worker, so it may also be run on a contributor's own machine; the engine's run is CI's.

**A replay.** The workflow also runs on `workflow_dispatch` with a `base` and a `head`, each a full commit id: the lane of the dispatched ref over that recorded diff, so a change to the lane is measured against a run the lane already made. The script copies its own checkout's `tests/mutation_oracle.py` into the scratch tree, so the replay of an older head confines its oracle as today's plugin does.

**The budget is the designed limit.** mutmut gets 2,400 s and the job 55 minutes. The window bounds a small edit's mutants, not a large diff's: a diff that writes new functions keeps nearly all of theirs ([#1753](https://github.com/aallan/vera/pull/1753)'s 577 mutants hold 526 in the window), a refactor across many functions keeps thousands ([#1773](https://github.com/aallan/vera/pull/1773)'s 16,031 hold 5,151), and each surviving mutant runs every test that reaches its function. Such a run ends with the partial table: with no survivor among the mutants it decided and every changed function with one decided, exit 0 and the headline `Incomplete: the budget ran out before every mutant was decided.`, which the job summary and the annotation show; with a changed function that had none decided, exit 3. Branch protection's required list is synced by hand and does not name the job.

**What it adds to a pull request's own mutants.** A fix pull request still runs its hand-written mutants, one per mechanism it adds, deletes or moves; the lane adds mutmut's systematic mutants over the lines it changes. A survivor is triaged as in § Triaging a survivor: a weak test to strengthen, or an equivalent mutant to mark `# pragma: no mutate` with its reason.

**Blind spots of the engine.** mutmut 3 mutates no decorated function bar one whose only decorator is `@staticmethod` or `@classmethod` (a `@contextlib.contextmanager` helper has no mutants), no method of a nested class, no module-level or class-body code, no `__new__`, `__getattribute__` or `__setattr__`, and no triple-quoted string, so a docstring is never mutated. A function that runs only at import time (called by module-level code, or a dataclass field's default, and by nothing that runs after) is mutated, but its mutants can never be killed in process: mutmut 3 forks each mutant's worker after the modules are imported, so the mutated function never runs. One that a test also calls runs under its mutant then, and its mutants can be killed. The nightly sweep runs their mutants like any other and reports such a function's survivors apart, by rule, outside the score (§ The cycle's survivors, [#1740](https://github.com/aallan/vera/issues/1740)); this lane still reports a changed one's mutants as survivors. The lane lists a changed function of the kinds mutmut does not mutate as not mutated, with the reason, and counts the changed lines outside every function.

```bash
python scripts/mutate_diff.py                                   # origin/main...HEAD, 2,400 s budget
python scripts/mutate_diff.py --base <sha> --budget 600 --json out.json

```
